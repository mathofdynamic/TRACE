# Repository Memory and a Portable `.trace` Standard

**Deep Research Report — Query 3**  
**Research date:** 4 August 2026  
**Scope:** Repository-resident AI memory, engineering decisions, change intelligence, agent instructions, governance metadata, local/cloud generation, and dashboard synchronization.

---

## Executive assessment

No active product or open standard currently provides the complete system proposed for `.trace`.

The market is fragmented across several partially overlapping layers:

1. **Agent instruction files** such as `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.cursor/rules/`, and `.windsurf/rules/` store project guidance for coding agents.
2. **Spec-driven development directories** such as GitHub Spec Kit, OpenSpec, and Kiro store requirements, design documents, implementation tasks, and archived change proposals.
3. **Decision and release conventions** such as Architecture Decision Records, Changesets, Towncrier, Scriv, Conventional Commits, and Keep a Changelog preserve selected rationale or release-facing changes.
4. **Repository memory systems** such as Cline Memory Bank and projectmem preserve project context or agent experience across sessions.
5. **Governance and machine-readable evidence formats** such as `CODEOWNERS`, Backstage entity descriptors, SARIF, in-toto attestations, SLSA provenance, and W3C PROV represent ownership, findings, or provenance in structured forms.
6. **Runtime interoperability protocols** such as the Model Context Protocol allow agents to consume resources and tools, but do not define a repository memory format.

The closest single implementation is **projectmem**, because it uses a local `.projectmem/` directory, typed append-only events, deterministic summaries, secret redaction, and an MCP interface.[^1][^2] It still does not meet the full `.trace` proposal: its raw event log is ignored by Git by default, conflict-free multi-user logs remain future work, and it does not define a broad vendor-neutral schema for PR analysis, daily reports, risks, rules, dashboard synchronization, and cloud/local interchange.

The strongest design precedent for avoiding Git conflicts is not an AI-memory product. It is the **change-fragment pattern** used by Changesets, Towncrier, and Scriv: each change creates an independent file, and a deterministic process later generates an aggregate changelog.[^3][^4][^5] `.trace` should adopt the same principle.

### Core conclusion

`.trace` can become meaningful, but only if it is defined narrowly as:

> **A portable, append-only repository ledger for software-change intelligence, engineering decisions, risks, rules, and evidence produced by humans, CI systems, local agents, or cloud services.**

It should **not** attempt to become a universal AI memory system, conversation archive, observability trace format, project-management database, or replacement for Git hosting platforms.

The recommended strategy is:

- Publish an **open, vendor-neutral draft specification**.
- Keep governance under Trace during a practical `0.x` incubation period.
- Build three first-party implementations: cloud producer, local Skill/CLI producer, and dashboard consumer.
- Validate it in real repositories before freezing `1.0`.
- Standardize the portable data layer while keeping higher-value analysis, coordination, policy enforcement, and dashboard UX proprietary.

## 1. Research question

This report investigates whether an existing product, convention, or open standard already supports a version-controlled repository directory that can contain:

- Daily change reports
- Pull-request analysis
- Engineering decisions
- Risks and technical debt
- Team rules and governance information
- References to commits, branches, pull requests, issues, and tasks
- Outputs generated by either a cloud service or a local coding agent
- Data synchronized with a central dashboard
- Human-readable documents and machine-readable records
- Portable consumption by multiple AI agents and vendors

It also proposes a practical initial specification for `.trace` and assesses its standardization potential.

## 2. Landscape taxonomy

The existing ecosystem should not be treated as one competitive category. Each group solves a different part of the repository-memory problem.

| Category | Representative systems | Primary purpose | Main gap relative to `.trace` |
|---|---|---|---|
| Agent instructions | `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, Copilot instructions, Cursor Rules, Windsurf Rules | Tell agents how to work | Mostly static guidance; little event history, provenance, or structured change intelligence |
| Agent capabilities | Agent Skills | Package reusable instructions, scripts, and references | Describes procedures, not repository history |
| Spec-driven development | Spec Kit, OpenSpec, Kiro Specs | Preserve requirements, plans, designs, and tasks | Focused on intended work, not an append-only record of actual changes and risks |
| Decision records | ADR, MADR | Record important architectural decisions | Narrow artifact type; mostly manual; weak machine interoperability |
| Changelog fragments | Changesets, Towncrier, Scriv | Record release-facing changes without shared-file conflicts | Limited to release notes and package versions |
| Repository memory | Cline Memory Bank, projectmem, GitMem, Claude-Mem | Preserve context and lessons across agent sessions | Often vendor-specific, mutable, local-only, or not fully committed to Git |
| Governance | `CODEOWNERS`, repository rulesets | Assign ownership and enforce repository policy | No history, reasoning, or AI-generated reports |
| Software catalog metadata | Backstage `catalog-info.yaml` | Describe components, owners, systems, and relationships | Current-state catalog, not development history |
| Findings interchange | SARIF | Exchange static-analysis findings | Narrow to analysis results; not project memory or decisions |
| Provenance | in-toto, SLSA, W3C PROV | Prove who or what produced an artifact | Does not provide engineering narratives, risk records, or daily reports |
| Agent interoperability | MCP | Let clients consume tools, prompts, and resources | Transport/runtime protocol, not a Git storage convention |

## 3. Detailed review of existing approaches

## 3.1 Agent instruction and context files

### 3.1.1 `AGENTS.md`

`AGENTS.md` is the strongest emerging cross-vendor convention for repository-level agent instructions. It is deliberately simple: plain Markdown placed in a repository, with nested files able to provide more specific guidance to subtrees. The project describes the format as open and reports adoption across more than 60,000 open-source projects.[^6]

**Typical structure**

```text
repository/
├── AGENTS.md
├── packages/
│   ├── frontend/
│   │   └── AGENTS.md
│   └── backend/
│       └── AGENTS.md
└── src/
```

**Format and schema**

- Plain Markdown
- No mandatory headings or formal schema
- Scope is inferred from filesystem location
- The closest applicable file generally takes precedence

**Versioning and Git behavior**

- Normally committed to Git
- Versioned through normal repository history
- Merge conflicts are ordinary text conflicts

**Consumption**

- Read directly by coding agents
- Human-readable as repository documentation
- No standard dashboard or query model

**Strengths**

- Minimal adoption friction
- Vendor-neutral positioning
- Easy human review
- Nested scope works naturally in monorepos

**Failure modes**

- No required metadata, identifiers, ownership, timestamps, or provenance
- Conflicting nested instructions may be interpreted differently by vendors
- Free-form text is difficult to validate mechanically
- It describes expected behavior, not what happened
- Large instruction files consume context and can become stale

**Relevance to `.trace`**

`AGENTS.md` should be treated as an adjacent standard, not replaced. `.trace` should reference applicable instruction files and optionally expose structured rules, but it should not become another general agent-prompt convention.

---

### 3.1.2 Vendor-specific instruction systems

#### Claude Code

Claude Code distinguishes team-authored project memory from agent-authored automatic memory. `CLAUDE.md`, `.claude/rules/*.md`, and local variants can provide hierarchical instructions; project files can be committed, while automatic memory is stored outside the repository in a per-project local location.[^7]

This separation is important: **shared project truth and private adaptive memory are different data classes**. `.trace` should preserve the same distinction.

#### GitHub Copilot

GitHub supports repository-wide `.github/copilot-instructions.md` and path-specific `.github/instructions/**/*.instructions.md` files. Instructions may be used by Copilot chat, coding agent, and code review depending on the surface and configuration.[^8]

The files are portable within GitHub’s ecosystem but their applicability and precedence vary across IDEs and Copilot surfaces. They remain guidance rather than historical evidence.

#### Cursor

Cursor stores project rules under `.cursor/rules/`, commonly using MDC files containing metadata and Markdown content.[^9] Rules can be scoped or automatically selected. The older single `.cursorrules` file has been superseded by the directory model.

Cursor Rules demonstrate the value of **small scoped files with metadata**, but MDC is vendor-specific and does not define records, provenance, or synchronization.

#### Windsurf

Windsurf separates automatically generated local memories from shareable repository rules. Shared rules can live in `.windsurf/rules/*.md` or `AGENTS.md`, while automatic memories are stored locally and are not version-controlled.[^10]

This reinforces a useful boundary for `.trace`: private agent adaptation should not be committed by default.

#### Gemini CLI

Gemini CLI loads hierarchical `GEMINI.md` files and can route durable information into shared project files, private per-project memory, or global user memory.[^11][^12]

Its routing model is conceptually strong, but the files remain Markdown instructions without a cross-vendor historical schema.

### Cross-system assessment

Instruction files have achieved real adoption because they are simple and visible. Their weaknesses are equally consistent:

- They mix policy, architecture, commands, and preferences in prose.
- They are mutable shared documents.
- Precedence rules differ by agent.
- No standard identifies the author, generating model, evidence, source branch, or relevant Git objects.
- They are trusted as executable context, creating prompt-injection and memory-poisoning risk.

Recent research is mixed on their practical effect. A 2026 study of 15,549 agentic pull requests found that instruction files did not consistently improve merge outcomes across projects.[^13] Other studies report quality problems and contradictory guidance in agent manifests. The implication is not that instructions are useless; it is that **unstructured context is not a reliable governance or evidence layer**.

## 3.2 Agent Skills

Agent Skills define an open folder format centered on a required `SKILL.md` file with YAML front matter and Markdown instructions. Skills may bundle scripts, references, templates, and other resources.[^14][^15]

```text
my-skill/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

The format is supported beyond one vendor, including Anthropic, OpenAI, and Microsoft tooling.[^15][^16]

**Strengths**

- Portable capability packaging
- Progressive disclosure reduces context cost
- Can include executable local tooling
- Suitable for distributing a `.trace` generator, validator, or renderer

**Failure modes**

- `SKILL.md` bodies remain largely unstructured
- Skills are executable supply-chain artifacts and require trust controls
- A skill can produce any output; it does not standardize that output
- Skills are capabilities, not project history

Research published in 2026 found widespread quality “smells” in sampled `SKILL.md` files and demonstrated semantic supply-chain attacks against skill discovery and selection.[^17][^18] Therefore a `.trace` Skill should be signed or pinned, operate with least privilege, and never treat third-party instructions as trusted repository facts.

**Relevance to `.trace`**

Agent Skills are an excellent **distribution mechanism** for local `.trace` production, but not the data standard itself.

## 3.3 Architecture Decision Records

Architecture Decision Records preserve a consequential decision, its context, considered options, and consequences. MADR provides a structured Markdown template and tooling-friendly convention.[^19]

Common layout:

```text
docs/
└── decisions/
    ├── 0001-use-postgresql.md
    ├── 0002-adopt-event-sourcing.md
    └── 0003-supersede-0001.md
```

**Versioning strategy**

- ADRs are generally immutable after acceptance
- New records supersede old decisions instead of rewriting history
- Git provides authorship and chronological history

**Merge behavior**

- One decision per file reduces conflicts
- Numeric identifiers can conflict when parallel branches allocate the same next number
- UUIDs, timestamps, or coordinated numbering reduce collisions

**Consumption**

- Primarily human-readable
- Can be indexed by documentation systems and agents
- Machine parsing depends on local templates or front matter

**Strengths**

- Strong mental model for decision history
- Explicit status and supersession
- Durable and reviewable

**Failure modes**

- Usually manual and inconsistently maintained
- No universal schema
- Weak linkage to exact commits, PRs, evidence, or generating systems
- Often captures only architectural decisions, not operational risk or daily change intelligence

**Relevance to `.trace`**

`.trace` should copy ADR semantics: immutable records, explicit status, stable identifiers, and `supersedes` relationships. Existing ADR directories should be referenced rather than forcibly migrated.

## 3.4 Changelogs and change-fragment systems

### Keep a Changelog and Conventional Commits

Keep a Changelog recommends a curated chronological record of notable user-facing changes.[^20] Conventional Commits standardizes commit-message structure so tools can infer release impact and automate versioning.[^21]

These conventions are useful inputs, but neither stores full engineering memory.

### Changesets

Changesets creates one Markdown file with YAML front matter per change under `.changeset/`. The file is committed with the branch and later consumed to update versions and changelogs.[^3][^22]

```text
.changeset/
├── config.json
├── quiet-dogs-smile.md
└── warm-taxis-run.md
```

Each fragment contains:

- A package or component set
- A semantic-version bump type
- A human-readable change summary

**Conflict strategy**

Independent, uniquely named files allow parallel branches to add changes without editing one shared changelog. Multiple fragments can stack safely.

### Towncrier

Towncrier explicitly avoids a monolithic changelog. Each pull request creates a small “news fragment” named with a ticket identifier and change type; the release process aggregates fragments into a digest.[^4]

### Scriv

Scriv follows the same model using a configurable fragment directory, `changelog.d/` by default. Fragments are normally committed with the code and later aggregated using `scriv collect`.[^5]

### Lessons for `.trace`

This family provides the clearest proven answer to merge conflicts:

- Never have every producer append to one committed `events.jsonl` file.
- Never make daily reports the canonical write target.
- Write one immutable record per event.
- Generate aggregate views deterministically.
- Let CI or one designated actor own generated shared summaries.

## 3.5 Spec-driven repository directories

### GitHub Spec Kit

Spec Kit stores feature artifacts under `specs/<feature>/`, including `spec.md`, `plan.md`, `tasks.md`, research, data models, contracts, and quick-start validation material.[^23]

```text
specs/
└── 003-chat-system/
    ├── spec.md
    ├── plan.md
    ├── research.md
    ├── data-model.md
    ├── quickstart.md
    ├── tasks.md
    └── contracts/
```

A `.specify/` directory stores templates, scripts, project constitution, and active-feature state.[^24]

**Strengths**

- Rich intent and implementation context
- Reviewable Markdown artifacts
- Multiple agent integrations
- Strong lifecycle from specification to execution

**Failure modes**

- Peer documents can diverge as implementation changes
- Artifacts are mutable rather than append-only
- Primarily describes intended work
- No common event schema or producer provenance

Spec Kit documentation now explicitly discusses keeping `spec.md`, `plan.md`, and `tasks.md` aligned after discoveries, confirming that drift is a core lifecycle problem.[^25]

### OpenSpec

OpenSpec organizes each proposed change as a folder containing proposal, design, tasks, and specification deltas. Completed work is moved to an archive.[^26][^27]

```text
openspec/
├── specs/
└── changes/
    ├── add-dark-mode/
    │   ├── proposal.md
    │   ├── design.md
    │   ├── tasks.md
    │   └── specs/
    └── archive/
```

OpenSpec’s per-change folder provides parallelism, reviewability, and preserved context. It claims compatibility with more than 30 AI assistants.[^27]

**Strengths**

- Clear change lifecycle
- Change folders reduce conflict
- Preserves “why” alongside proposed implementation
- Tool-agnostic positioning

**Failure modes**

- Intended-state specification, not complete actual-change evidence
- Mostly Markdown conventions rather than a strict event schema
- Requires discipline to reconcile implementation with specs
- No built-in universal identity, source attribution, or dashboard synchronization protocol

### Kiro Specs

Kiro stores `requirements.md`, `design.md`, and `tasks.md` under `.kiro/specs/`. The same artifacts are shared across Kiro surfaces, and Kiro recommends committing them with the code.[^28][^29]

```text
.kiro/
└── specs/
    └── user-authentication/
        ├── requirements.md
        ├── design.md
        └── tasks.md
```

Kiro demonstrates product value in treating structured planning artifacts as persistent repository history. It remains a vendor-specific workflow and does not define a general change ledger.

### Relevance to `.trace`

Spec systems should be **linked as evidence and intent sources**, not copied wholesale into `.trace`. A `.trace` record can reference a Spec Kit, OpenSpec, or Kiro artifact and state whether implementation satisfied, modified, or contradicted it.

## 3.6 Repository memory systems

### Cline Memory Bank

Cline Memory Bank is a Markdown documentation methodology built around a small set of persistent context files such as `projectbrief.md`, `productContext.md`, `systemPatterns.md`, `techContext.md`, `activeContext.md`, and `progress.md`.[^30]

```text
memory-bank/
├── projectbrief.md
├── productContext.md
├── systemPatterns.md
├── techContext.md
├── activeContext.md
└── progress.md
```

**Strengths**

- Easy to understand and edit
- Captures project state beyond a README
- Works with ordinary Git
- Useful for session continuity

**Failure modes**

- Shared mutable files create merge conflicts
- Facts, plans, decisions, and temporary status can mix together
- No stable identifiers or schema
- No provenance or source evidence
- Stale text can remain active indefinitely
- Different agents can overwrite one another’s interpretation

Cline Memory Bank is a useful documentation pattern, but it is not a reliable interchange ledger.

### projectmem

projectmem is the closest existing implementation to the proposed `.trace` concept. It is a 2026 open-source, local-first memory layer for AI coding agents. It records typed events such as issues, attempts, fixes, decisions, and notes, then deterministically projects them into summaries exposed through MCP.[^1][^2]

Representative structure:

```text
.projectmem/
├── events.jsonl
├── summary.md
├── PROJECT_MAP.md
├── AI_INSTRUCTIONS.md
├── issues/
├── .current_issue
└── viz.html
```

**Data model**

- Append-only typed events
- JSON Lines source log
- Deterministic Markdown summary
- References between issues, attempts, fixes, and decisions

**Privacy behavior**

- Local-first operation
- Default redaction mechanisms
- No mandatory cloud account or telemetry

**Git behavior**

The project normally commits distilled files while ignoring the raw `events.jsonl` and runtime state. This is reasonable for private local memory but weakens team portability because the canonical event source is not necessarily version-controlled.[^31]

**Conflict handling**

A shared `events.jsonl` file would be a conflict hotspot. The project’s research roadmap identifies conflict-free multi-user logs as future work, indicating that collaborative repository synchronization is not fully solved.[^2]

**Strengths**

- Event-sourced model
- Deterministic projections
- Local-first privacy
- MCP access across agents
- Explicit distinction between raw events and summaries

**Failure modes**

- Early-stage adoption
- Canonical log not committed by default
- Multi-user conflict resolution incomplete
- Narrower event taxonomy than `.trace`
- No standard cloud producer/dashboard synchronization contract
- No vendor-neutral conformance suite

### Vendor-managed and local memory products

Systems such as GitHub Copilot memory, Claude automatic memory, Claude-Mem, and GitMem preserve useful information across sessions, but generally store it in vendor infrastructure, local databases, or proprietary layouts. They may improve continuity, but they do not provide a transparent, version-controlled interchange format.

The distinction is critical:

- **Agent memory** optimizes future model behavior.
- **Repository evidence** documents what happened and why.

`.trace` should prioritize the second. Agent-specific memory can be generated from `.trace`, but should not be treated as the authoritative source.

## 3.7 Governance, metadata, and analysis formats

### `CODEOWNERS` and repository rulesets

`CODEOWNERS` maps paths to responsible users or teams and can be combined with branch protections to require owner review.[^32] Repository rulesets and protected branches can enforce status checks, review requirements, signed commits, and other controls.[^33]

These files and platform settings represent enforceable governance, not narrative memory. `.trace` should reference them and record policy evaluations, but not duplicate ownership logic as a competing source of truth.

### Backstage `catalog-info.yaml`

Backstage stores software catalog descriptors in human-maintainable YAML and represents them as JSON through APIs. Entities commonly contain `apiVersion`, `kind`, metadata, ownership, lifecycle, and relationships.[^34]

Backstage demonstrates a successful hybrid pattern:

- Repository-resident declarative metadata
- Central ingestion and indexing
- Human-readable source files
- Machine-readable API representation
- Extensible entity kinds and annotations

This is directly relevant to `.trace` dashboard synchronization. However, Backstage primarily models current software entities, not immutable change events.

### SARIF

SARIF 2.1.0 is a standardized JSON format for static-analysis results. GitHub can ingest SARIF produced by different tools and display findings in code-scanning dashboards.[^35]

SARIF proves that a structured interchange format can create a multi-vendor analysis ecosystem. Its limitations relative to `.trace` are intentional: it models analysis runs, rules, locations, and results—not decisions, daily summaries, project rules, or persistent engineering memory.

A `.trace` PR-analysis record should link to SARIF artifacts rather than embed large duplicate findings.

### in-toto, SLSA, and W3C PROV

in-toto and SLSA define authenticated provenance for software artifacts and build processes.[^36][^37] W3C PROV models entities, activities, and agents.[^38]

These standards provide design guidance for source attribution:

- Identify the producer
- Identify the activity that created a record
- Identify source materials and resulting artifacts
- Use cryptographic digests
- Support signed attestations

They do not provide a human engineering narrative. `.trace` should borrow their provenance concepts without attempting to replace them.

## 3.8 Model Context Protocol

The latest MCP specification, dated 28 July 2026, defines a standard protocol through which LLM applications can access resources, prompts, and tools.[^39] Resources are uniquely identified by URIs, while tools expose machine-readable input schemas.[^40]

MCP is highly relevant to consumption:

- A local `.trace` server can expose query and write tools.
- Different IDEs and coding agents can consume the same repository records.
- A dashboard connector can expose filtered records to agents.

MCP does **not** solve:

- Directory layout
- Git merge behavior
- Record schemas
- Immutability
- Privacy exclusions
- Provenance of generated files
- Cloud/local synchronization semantics

Therefore MCP should be an optional access layer over `.trace`, not the storage specification.

## 5. Does an equivalent to `.trace` already exist?

### Direct answer

**No.** No reviewed system combines all of the following in one portable repository contract:

- Daily engineering summaries
- Pull-request analysis
- Decisions and supersession
- Risk and technical-debt tracking
- Team rules and governance references
- Stable links to commits, issues, tasks, and pull requests
- Both local-agent and cloud-service production
- Version-controlled canonical records
- Deterministic human-readable projections
- Central dashboard synchronization
- Multi-vendor agent consumption

### Closest components

| Needed `.trace` capability | Strongest existing precedent |
|---|---|
| Open agent-facing repository guidance | `AGENTS.md` |
| Portable local capability packaging | Agent Skills |
| Immutable decision history | ADR / MADR |
| Conflict-resistant parallel records | Changesets, Towncrier, Scriv |
| Requirements/design/task history | OpenSpec, Spec Kit, Kiro |
| Event-sourced agent memory | projectmem |
| Repository metadata → central dashboard | Backstage descriptors |
| Multi-tool findings interchange | SARIF |
| Producer and artifact provenance | in-toto, SLSA, W3C PROV |
| Multi-agent runtime access | MCP |

The opportunity for Trace is not inventing every primitive. It is defining the **integration contract** between these established ideas.

## 6. Design principles for an open `.trace` specification

## 6.1 Scope principle

The standard should store **durable engineering knowledge tied to software changes**.

It should include:

- What changed
- Why it changed
- What evidence supports the analysis
- What decision or risk was created or modified
- Which Git objects and external work items are involved
- Who or what produced the record
- Which previous record it supersedes or relates to

It should exclude by default:

- Full chat transcripts
- Hidden chain-of-thought or private model reasoning
- Raw prompts and responses
- Complete source-code diffs
- Build logs and binary artifacts
- Credentials, tokens, environment variables, and secrets
- Personal user profiles or unrelated behavioral memory
- Absolute local filesystem paths
- Vendor telemetry identifiers without explicit consent

---

## 6.2 Canonical records versus generated views

The most important architectural decision is to separate **canonical records** from **generated views**.

### Canonical records

- Machine-readable JSON
- One immutable record per file
- Stable identifier
- Strict JSON Schema validation
- Committed to Git unless repository policy excludes a record class
- Never edited after publication; corrections create a new record

### Human narratives

- Optional Markdown sidecar associated with one canonical record
- Used for longer explanations, decision rationale, and review notes
- Must not contain required machine metadata that is absent from the JSON record

### Generated views

- Daily reports
- PR summaries
- Current risk register
- Decision index
- Team activity report
- Project timeline

Views are deterministic projections. They are not the source of truth. They may be committed for browsing, generated only in CI, or ignored locally according to repository policy.

This avoids the dual-source problem in which Markdown and JSON independently claim authority.

```text
│
├── schemas/
│   ├── record-0.1.schema.json
│   └── manifest-0.1.schema.json
│
└── runtime/                  # MUST be ignored by Git
    ├── indexes/
    ├── sync-state.json
    ├── locks/
    └── cache/
```

### Why this structure

- Date partitioning prevents oversized directories.
- UUID-based filenames avoid branch collisions.
- Rules remain human-authored and reviewable.
- Runtime indexes and synchronization cursors stay out of Git.
- Views can be regenerated.
- Records from cloud and local producers use the same contract.

### Optional compact profile

Small repositories may use:

```text
.trace/
├── manifest.json
├── records/
└── README.md
```

All other directories should be optional.

## 6.4 Minimum required metadata

Every canonical record should include at least:

| Field | Purpose |
|---|---|
| `$schema` | Identifies the JSON Schema used for validation |
| `spec_version` | Declares the `.trace` specification version |
| `id` | Globally unique stable record identifier |
| `type` | Names the record type |
| `occurred_at` | Time the underlying event occurred |
| `recorded_at` | Time the record was created |
| `title` | Short human-readable label |
| `summary` | Concise factual description |
| `repository_id` | Stable identifier for the repository |
| `producer` | Human, agent, cloud service, CI job, or importer that created it |
| `git` | Relevant Git object identifiers and ref context |
| `references` | PRs, issues, tasks, specs, ADRs, or external evidence |
| `classification` | Public, internal, confidential, or restricted policy class |
| `content_digest` | Digest of the canonical normalized record content |

Recommended but optional:

- `confidence`
- `evidence`
- `impacts`
- `owners`
- `tags`
- `related_records`
- `supersedes`
- `generated_from`
- `narrative_path`
- `attestation`

## 6.5 Proposed core record types

The initial standard should keep a small controlled taxonomy:

- `change.summary`
- `pull_request.analysis`
- `review.finding`
- `decision`
- `risk`
- `technical_debt`
- `rule.change`
- `requirement.result`
- `incident.note`

Unknown namespaced types must remain readable and preservable even when a consumer cannot interpret their specialized fields.

## 6.7 Stable identifiers

Use **UUIDv7** for core record IDs. UUIDv7 is standardized in RFC 9562 and provides time-ordered identifiers without requiring a central sequence allocator.[^41]

Benefits:

- Negligible collision risk across local and cloud producers
- Sortable by creation time
- Safe parallel generation on branches
- No dependence on provider-specific issue numbers
- No leaking of machine identity or MAC address

Do not use sequential integers as the primary identifier. They create collisions across branches and require coordination.

Human-friendly aliases such as `ADR-0042` may exist as optional labels.

---

## 6.8 Git object references

Git references must include the hash algorithm because repositories may transition from SHA-1 to SHA-256.[^42]

Required practices:

- Store full object IDs, not abbreviated hashes.
- Declare `hash_algorithm`.
- Record both base and head commit for PR analysis.
- Store repository identity separately from remote URLs.
- Treat branch names as mutable labels, not stable identifiers.
- Prefer commit-bound path and line evidence.
- Allow references to tags, trees, blobs, and merge bases when needed.

A record tied only to `main` or `feature/auth` will become ambiguous after history changes. A record tied to a full commit object remains verifiable.

---

## 6.9 Source attribution and trust

Every producer must declare:

- Producer kind: `human`, `local-agent`, `cloud-service`, `ci`, or `importer`
- Product and version
- Execution identifier
- Generation timestamp
- Input Git state
- Optional model provider/name/version
- Optional configuration or policy digest
- Optional signature or attestation

The standard should separate:

1. **Authorship** — who or what wrote the record
2. **Evidence** — what repository objects or external sources support it
3. **Confidence** — how certain the producer claims to be
4. **Integrity** — whether the record has changed
5. **Authority** — whether repository policy treats that producer as trusted

A model-generated statement must never be considered true only because it exists in `.trace`.

Optional signed provenance should be compatible with in-toto-style attestations rather than inventing a new signature framework.

---

## 6.10 Local versus cloud-generated output

The same schema must be used by both execution modes.

### Local producer

- Runs as a CLI, Agent Skill, IDE extension, or MCP server
- Reads the local working tree and Git metadata
- Writes canonical records directly
- Can operate without an account
- May keep private caches in `.trace/runtime/`

### Cloud producer

- Runs as a GitHub App, GitLab integration, CI job, or Trace service
- Analyzes a specific base/head commit pair
- Writes records through a pull request, bot commit, downloadable bundle, or synchronization API
- Must declare the exact analyzed Git state
- Must not silently rewrite local records

### Hybrid workflow

1. Local agent creates records.
2. Records are committed with code.
3. Dashboard ingests them by ID and digest.
4. Cloud analysis creates additional records for the same PR.
5. The dashboard links related records without merging their claims.
6. A deterministic renderer creates a consolidated PR view.

Cloud and local outputs should coexist, not overwrite one another.

---

## 6.11 Conflict prevention

The standard should make conflict avoidance structural rather than relying on custom Git merge drivers.

### Required rules

1. **One immutable canonical record per file.**
2. **Never use one committed append-only log shared by all producers.**
3. **Never mutate a record after merge.**
4. **Corrections create a new `record.correction` record.**
5. **Status transitions create new records referencing the prior record.**
6. **Generated aggregate views have one designated writer, normally CI.**
7. **UUIDv7 filenames prevent branch allocation conflicts.**
8. **Runtime locks and indexes remain ignored by Git.**

### Optional behavior

- A renderer may sort records by `(occurred_at, id)`.
- Generated views may include a digest of their input record set.
- CI may reject direct human edits to generated views.
- A repository may omit committed views and render them only in the dashboard.

Custom merge drivers may improve generated-view handling, but conformance must not depend on them.

---

## 6.12 Sensitive-data exclusions

Repository memory is a durable security boundary. Once sensitive data is committed, deletion is difficult because it remains in Git history.

The specification should prohibit by default:

- API keys, passwords, tokens, cookies, private keys, and credentials
- Raw environment files
- Full prompts or chat transcripts
- Personal email content or private messages
- Personal data not needed for engineering accountability
- Absolute local paths containing usernames
- Proprietary source excerpts from external repositories
- Full production logs
- Customer data and database samples
- Hidden reasoning or chain-of-thought
- Unredacted vulnerability exploit details in public repositories

GitHub push protection demonstrates the importance of blocking secrets before they enter repository history.[^43] `.trace` implementations should run secret scanning and policy validation before every write.

### Required privacy controls

- `classification` on every record
- Repository-wide allow/deny policy
- Redaction report when content is removed
- Maximum evidence excerpt length
- Path filtering similar to `.gitignore`
- No raw transcript capture by default
- Private runtime directory ignored by Git
- Optional “metadata-only” mode
- Dashboard access controls independent of repository visibility

Suggested policy file:

```json
{
  "spec_version": "0.1.0",
  "default_classification": "internal",
  "commit_records": true,
  "commit_views": false,
  "allow_prompt_content": false,
  "allow_source_excerpts": false,
  "max_record_bytes": 262144,
  "max_narrative_bytes": 131072,
  "excluded_paths": [
    ".env*",
    "secrets/**",
    "customer-data/**",
    "**/*.pem",
    "**/*.key"
  ]
}
```

---

## 6.13 Repository-size control

A memory standard can damage the repository if it stores every agent action, full diff, test log, or repeated summary.

Recommended defaults:

- Maximum canonical record: **256 KiB**
- Maximum Markdown narrative: **128 KiB**
- No binary attachments in Git by default
- No duplicated diffs
- Evidence stored as references and hashes
- Large artifacts stored externally or in Git LFS with immutable digest references
- Daily and weekly reports generated from records rather than copied into each record
- Configurable retention for low-value transient record types
- Periodic compaction only through a signed manifest, never silent deletion

### Retention classes

| Class | Example | Default retention |
|---|---|---|
| Permanent | Accepted decision, resolved major risk, release record | Repository lifetime |
| Long | PR analysis, requirement result, incident note | Configurable, normally retained |
| Short | Duplicate warning, temporary coordination note | 30–180 days or dashboard-only |
| Runtime | Embeddings, indexes, caches, locks | Never committed |

The standard should encourage **distillation, not exhaustive surveillance**.

---

## 6.14 Schema versioning

Use semantic versioning for the specification and JSON Schema Draft 2020-12 for record validation.[^44]

Rules:

- `MAJOR`: breaking semantic or structural changes
- `MINOR`: backward-compatible fields or record types
- `PATCH`: clarifications and non-semantic corrections
- Every record declares `spec_version`
- Every record includes a `$schema` URI
- Consumers must preserve unknown extension fields
- Consumers may reject unsupported major versions
- Producers must not write fields whose meaning changes without a major version
- Repository manifests may declare accepted version ranges

During `0.x`, breaking changes are expected but must be accompanied by deterministic migration tools.

## 6.15 Interoperability profiles

A single “supports `.trace`” claim would be too vague. Define conformance profiles.

### Core Reader

- Parses manifest and canonical records
- Validates required fields
- Preserves unknown extensions
- Resolves related-record references

### Core Writer

- Produces valid immutable records
- Generates UUIDv7 IDs
- Calculates content digests
- Respects policy and privacy rules

### Local Agent Producer

- Records local Git state
- Identifies itself and execution context
- Writes without cloud dependency
- Supports dry-run and review-before-commit

### Cloud Producer

- Binds analysis to exact base/head commits
- Uses idempotent synchronization
- Declares tenant/service provenance
- Never changes local records in place

### Dashboard Consumer

- Ingests by record ID and digest
- Handles repository forks and branch divergence
- Shows source and trust state
- Supports deletion/access policy independently from Git

### Renderer

- Produces deterministic human views
- Declares input record IDs and renderer version
- Avoids making aggregate views canonical

### MCP Adapter

- Exposes read/query operations as MCP resources or tools
- Applies repository authorization
- Does not bypass `.trace` policy

## 6.16 Dashboard synchronization model

Synchronization should be content-addressed and idempotent.

### Recommended protocol behavior

1. Dashboard discovers `manifest.json`.
2. It enumerates canonical record paths.
3. It compares `id` and `content_digest` with already ingested records.
4. New records are uploaded or indexed.
5. An existing ID with a different digest is flagged as tampering or invalid mutation.
6. Deleted Git records are marked as absent from the current branch, not silently erased from dashboard history.
7. Branch and commit context are preserved.
8. Private dashboard annotations are stored outside `.trace` unless explicitly exported as new records.

### Sync state

Sync cursors and remote IDs must live in `.trace/runtime/sync-state.json` or user configuration, not committed canonical files.

### Forks

A fork inherits record IDs. The dashboard should identify records by:

```text
(repository_id, record_id, content_digest)
```

When a fork creates a new record, UUIDv7 avoids collision. When it modifies an inherited record, the mutation should be rejected and represented as a correction or supersession.

---

## 6.17 Human-readable versus machine-readable output

A common mistake is forcing one format to serve every purpose.

### Recommended contract

- **JSON record:** canonical facts, references, identity, provenance, evidence, and relationships
- **Markdown narrative:** optional long-form explanation for one record
- **Markdown view:** generated summary across multiple records
- **MCP/API representation:** transport view derived from the canonical JSON

YAML-front-matter Markdown is attractive for simplicity, as demonstrated by Agent Skills and Changesets, but it has disadvantages for a cross-vendor evidence ledger:

- YAML parsers differ on implicit types
- Canonical serialization and signing are harder
- Schema validation is less consistent
- Long free-form bodies encourage metadata leakage into prose

Therefore JSON should be canonical for `.trace` even if most users interact with rendered Markdown.

---

## 6.18 Rules and policy files

The `.trace/rules/` directory should not compete with `AGENTS.md`, `CODEOWNERS`, or vendor instruction files.

Recommended behavior:

- Human-authored rules remain Markdown.
- Each rule file has a stable rule identifier in front matter.
- Rules can reference external authoritative files.
- Analysis records state which rule IDs were evaluated.
- A rule-change event is written when a rule is added, changed, or removed.
- Enforcement remains the responsibility of CI, Git hosting rulesets, or Trace.

Example:

```markdown
---
id: rule:architecture:no-cross-domain-db-access
version: 3
status: active
owners:
  - team:platform-architecture
applies_to:
  - services/**
source_of_truth: .trace/rules/architecture-boundaries.md
---

# No cross-domain database access

Services must communicate across domain boundaries through declared APIs or events.
Direct queries into another service's database are prohibited.
```

This makes rules addressable without pretending Markdown alone guarantees enforcement.

## 6.19 Security threat model

`.trace` files will be consumed by humans and AI agents. This creates a threat model beyond ordinary documentation.

### Major threats

1. **Prompt injection:** malicious instructions embedded in records or narratives influence future agents.
2. **Memory poisoning:** false conclusions persist across sessions and become treated as project truth.
3. **Producer impersonation:** a record claims it came from an approved cloud service.
4. **Evidence substitution:** referenced branch or path changes while the record remains.
5. **Secret leakage:** analysis captures credentials or production data.
6. **Repository flooding:** a producer generates thousands of low-value records.
7. **Dashboard privilege escalation:** private records are synchronized into a broader audience.
8. **Model over-trust:** probabilistic analysis is presented as verified fact.

A July 2026 study found that payloads planted in persistent agent memory can successfully affect current and future sessions.[^45] This makes trust boundaries mandatory.

### Required mitigations

- Treat narrative content as untrusted data, not executable instructions.
- Separate rules from observations.
- Require producer identity and integrity digest.
- Allow repository policy to define trusted producers.
- Bind evidence to immutable commits.
- Secret-scan before write and before sync.
- Rate-limit and size-limit producers.
- Require explicit user approval before an agent promotes an observation into an authoritative rule.
- Display confidence and source prominently.
- Support signed attestations for high-trust producers.

## 7. Proposed `.trace` lifecycle

## 7.1 Initialization

```bash
trace init
```

Creates:

- `manifest.json`
- `policy.json`
- `README.md`
- schema references
- `.gitignore` entries for `.trace/runtime/`

The repository receives a random stable `repository_id` rather than deriving identity from a mutable remote URL.

## 7.2 Record creation

```bash
trace add decision
trace analyze-pr --base <commit> --head <commit>
trace report daily --date 2026-08-04
```

The producer:

1. Reads policy.
2. Collects only allowed evidence.
3. Creates a UUIDv7 record.
4. Runs secret scanning.
5. Validates JSON Schema.
6. Calculates digest.
7. Writes canonical JSON and optional narrative.
8. Does not commit automatically unless configured.

## 7.3 Review and commit

Records should be reviewed in the same pull request as the related code when practical. A repository may require:

- Trace schema validation
- No mutation of existing record IDs
- Size limits
- Secret scanning
- Trusted producer signatures for protected record types
- Deterministic view regeneration

## 7.4 Dashboard ingestion

The dashboard imports records by ID and digest, resolves references, and creates query indexes. It may enrich records with private data, but enrichment remains outside the committed canonical file unless explicitly exported.

## 7.5 Supersession and correction

Records remain immutable.

Examples:

- A resolved risk creates a new `risk` record with `status: resolved` and `supersedes` the earlier record.
- A wrong PR analysis creates `record.correction` referencing the invalid claim.
- A new architectural decision supersedes an ADR-linked decision record.

## 7.6 Rendering

```bash
trace render daily 2026-08-04
trace render pr github:482
trace render risks
```

Views include:

- Renderer version
- Input record IDs
- Generation timestamp
- Optional input-set digest

This allows CI to verify that committed views are current.

## 8. Adoption and interoperability assessment

## 8.1 Why `.trace` has a real opening

The ecosystem is converging on repository-resident agent context, but formats remain fragmented. Several trends support an open format:

- `AGENTS.md` shows cross-vendor appetite for simple repository conventions.[^6]
- Agent Skills show that capability folders can become portable across platforms.[^14][^16]
- Spec Kit, OpenSpec, and Kiro show demand for committed planning artifacts.[^23][^27][^29]
- Changesets and Towncrier prove per-change fragments can scale without constant changelog conflicts.[^3][^4]
- projectmem validates local-first event-sourced agent memory and MCP consumption.[^1][^2]
- SARIF and Backstage demonstrate that repository or build-produced structured data can feed central dashboards across tools.[^34][^35]
- MCP provides a common runtime layer for exposing repository records to agents.[^39][^40]

The missing layer is a coherent portable ledger tying actual software changes to decisions, risks, rules, and evidence.

## 8.2 Barriers to standardization

### 1. Generated-file resistance

Many teams dislike committing machine-generated files because they add noise, create review burden, and grow repository history.

**Response:** keep canonical records compact, event-based, and policy-controlled. Make views optional.

### 2. Weak incentive for competing vendors

Code-review vendors may prefer proprietary dashboards and data models.

**Response:** make `.trace` useful without their participation. Offer an exporter/importer SDK and let customers demand portability.

### 3. Schema overreach

Trying to model every engineering activity will create a complex, unstable specification.

**Response:** small core fields, controlled core types, namespaced extensions.

### 4. Trust and security

AI-generated repository memory can preserve false or malicious instructions.

**Response:** distinguish observations from rules, require provenance, bind evidence to commits, and treat narratives as untrusted.

### 5. Git conflict and size costs

A naïve `events.jsonl` or daily-file design will fail under parallel branches.

**Response:** immutable UUID record fragments and deterministic projections.

### 6. Terminology collision

“Trace” already has established meanings in distributed observability through OpenTelemetry and as Apple Instruments `.trace` documents.[^46][^47]

**Response:** consistently call the format **Trace Repository Memory** or **Trace Engineering Ledger** in technical documentation. Keep `.trace/` as the directory, but avoid generic “trace format” wording and use namespaced schema/media identifiers.

## 9. Open standard or internal product format?

### Option A — Fully internal proprietary format

**Advantages**

- Faster iteration
- No compatibility obligations
- Easier product-specific optimization

**Disadvantages**

- Weak trust for repository-resident data
- Vendor-lock-in concern
- Harder adoption by local agents and third-party tools
- Customers may refuse to commit proprietary opaque metadata
- Competitors can define the open layer first

**Assessment:** strategically weak.

### Option B — Immediate formal open standard

**Advantages**

- Strong public positioning
- Easier ecosystem narrative
- Potential vendor participation

**Disadvantages**

- Premature governance overhead
- Unproven schema decisions become difficult to change
- Risk of designing by committee before real usage
- “Standard” claim lacks legitimacy without independent implementations

**Assessment:** premature.

### Option C — Open specification under product-led incubation

**Advantages**

- Transparent and portable from day one
- Fast `0.x` iteration remains possible
- Trace controls reference implementations and roadmap
- Third parties can build readers and exporters
- Product moat remains in analysis, coordination, UX, and managed synchronization

**Disadvantages**

- Requires good documentation, migration tools, and compatibility discipline
- Competitors can implement the format
- Governance expectations will grow if adoption succeeds

**Assessment:** strongest option.

### Recommendation

Start `.trace` as an **openly documented, vendor-neutral specification owned and incubated by Trace**, with a permissive reference implementation.

Do not call it an industry standard until all of these conditions are met:

1. At least two independent producers can write compatible records.
2. At least two independent consumers can read them.
3. Cloud and local records coexist in real repositories without recurring merge conflicts.
4. Privacy controls survive security review.
5. Repository-size behavior is measured over at least several months.
6. Migration from two `0.x` versions has been tested.
7. One third-party tool adopts the format without relying on Trace internals.
8. A stable `1.0` conformance suite exists.

After those conditions, governance can move to a neutral foundation or multi-vendor working group if that materially increases adoption.

## 10. Product strategy implications for Trace

The format itself should not be the primary monetization layer.

### Open layer

- `.trace` directory specification
- JSON Schemas
- Validation CLI
- Basic renderer
- Local Agent Skill
- MCP read adapter
- Import/export libraries
- Conformance tests

### Proprietary or managed layer

- High-quality PR and architecture analysis
- Cross-PR conceptual conflict detection
- Cross-repository intelligence
- Team and ownership inference
- Requirements and acceptance-criteria reconciliation
- Risk prioritization
- Reviewer suggestions
- Policy enforcement and merge gates
- Central dashboard and historical queries
- Enterprise access control and retention
- Managed cloud synchronization
- Organization-wide rules and analytics

This structure follows a strong commercial pattern: **open data contract, paid intelligence and coordination**.

A proprietary `.trace` format would make the product easier to copy at the UI level and harder to trust. An open format makes the repository data durable while Trace competes on analysis quality and workflow value.

## 12. Final verdict

`.trace` is not redundant. Existing systems solve separate fragments of the problem, and projectmem is the only reviewed implementation that approaches an event-sourced repository memory layer. Even projectmem does not deliver the proposed combination of portable committed records, PR intelligence, decisions, risks, team rules, local/cloud interchange, and central dashboard synchronization.

The opportunity is credible, but the initial concept must be tightened:

- Do not use a single shared event log.
- Do not make generated daily Markdown the canonical data.
- Do not store conversations or raw model memory.
- Do not duplicate existing authoritative files such as `AGENTS.md`, `CODEOWNERS`, ADRs, or specs.
- Do not claim a universal standard before independent adoption.

Build `.trace` as an **append-only, evidence-linked engineering ledger** with compact JSON records and generated Markdown views. Publish the contract, keep the implementation practical, and let Trace’s commercial value come from the quality of analysis and coordination built on top of it.

That direction has a realistic path to becoming an open standard. A broad “AI project memory folder” does not.

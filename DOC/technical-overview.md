# TRACE Technical Overview

## Document purpose

This document defines the technical direction for TRACE.

It is not a low-level implementation manual and does not replace the phased implementation prompts. It establishes the system boundaries, execution model, data contracts, security principles, analysis pipeline, and MVP constraints that all implementation work must follow.

The nontechnical product definition lives in [`project-overview.md`](./project-overview.md).

---

# 1. Technical product definition

TRACE is a repository-native software change intelligence and governance system.

It receives change events from Git repositories and local developer environments, analyzes those changes against project context and team rules, and emits portable artifacts into a versioned `.trace/` structure.

The same artifact contract must be supported across three execution modes:

1. **Cloud-managed execution**
2. **Local Skill/CLI execution**
3. **Hybrid execution**, where analysis remains local and selected artifacts synchronize to the TRACE control plane

The hosted dashboard is a control and presentation layer. It must not become the only source of truth for project intelligence.

---

# 2. Core technical principles

## 2.1 Repository-native artifacts

Every durable TRACE output must be representable inside `.trace/` using human-readable Markdown and machine-readable structured metadata.

The platform may maintain operational indexes in its database, but a user must be able to export the durable project record without losing its meaning.

## 2.2 One artifact contract across execution modes

Cloud, local, CI, and hybrid execution must produce artifacts that conform to the same schema.

The dashboard must not require artifacts to have been generated by TRACE Cloud. It must accept valid artifacts produced by the official CLI, an Agent Skill, CI, or a compatible third-party implementation.

## 2.3 Deterministic evidence before model inference

TRACE must collect deterministic facts before invoking a language model.

Examples:

- Git commits and diffs
- changed files and symbols
- branch and PR state
- test and CI results
- issue links
- ownership rules
- dependency relationships
- schema and migration changes
- existing TRACE decisions, risks, and policies

Language-model reasoning should synthesize, classify, compare intent, and explain impact. It should not replace facts that can be obtained deterministically.

## 2.4 Evidence-backed outputs

Every important finding must retain provenance.

A reader should be able to determine:

- which inputs supported the finding;
- whether it came from a deterministic rule, model reasoning, or both;
- when the evidence was collected;
- which model or execution environment produced the interpretation;
- whether a human accepted, rejected, or modified it.

## 2.5 Local-first privacy

TRACE must support a useful local mode in which source code does not need to be transmitted to TRACE Cloud.

Local execution cannot be a marketing-only mode that still depends on cloud code ingestion for core capabilities.

## 2.6 Sparse, high-signal interaction

The system must optimize for useful reviewer attention, not comment volume.

Style-only findings, speculative warnings, and duplicate comments should be suppressed by default. The product should prefer a short risk brief with evidence over many line comments.

## 2.7 No individual productivity scoring

TRACE may record authorship and ownership when needed to explain a change or route coordination work.

It must not generate productivity rankings, employee scores, keystroke tracking, or simplistic performance metrics derived from commit count, code volume, PR count, or AI usage.

# 3. System boundaries

TRACE consists of five primary product surfaces.

## 3.1 TRACE specification

The open, versioned contract that defines:

- `.trace/` directory conventions;
- artifact types;
- required metadata;
- identifiers and references;
- provenance fields;
- validation rules;
- compatibility and migration behavior.

The specification should remain implementation-independent.

## 3.2 TRACE CLI

The local execution engine.

Responsibilities include:

- inspecting repository state;
- reading Git history and active diffs;
- collecting project context;
- applying rules;
- running local parsers and integrations;
- calling the configured model provider when allowed;
- validating and writing `.trace/` artifacts;
- optionally synchronizing approved artifacts with TRACE Cloud.

The CLI is the canonical local runtime. Agent Skills should orchestrate the CLI rather than reimplement core behavior in prompts.

## 3.3 TRACE Agent Skill

A small set of instructions that teaches compatible coding agents how and when to invoke the TRACE CLI.

The Skill should:

- use progressive disclosure;
- avoid placing the entire TRACE manual into the model context;
- provide common workflows such as analyzing a PR, generating a daily report, validating artifacts, and preparing sync;
- never contain secrets;
- never become the authoritative analysis engine.

## 3.4 TRACE Cloud control plane

The hosted system for:

- organization and project management;
- Git provider installation management;
- policy and rule management;
- webhook intake;
- job orchestration;
- artifact ingestion and validation;
- dashboard views;
- report scheduling;
- team coordination;
- cross-repository analysis where permitted;
- audit and synchronization state.

## 3.5 TRACE analysis workers

Isolated execution processes that perform repository analysis for cloud-managed projects.

These workers may need to:

- clone repositories using short-lived credentials;
- build symbol and dependency indexes;
- execute analyzers;
- call model providers;
- produce artifacts;
- discard temporary source data according to policy.

The worker runtime must be separated from the public web application and webhook receiver.

# 4. Execution modes

## 4.1 Cloud-managed mode

### Flow

1. A user installs the TRACE GitHub App.
2. TRACE receives a repository or PR event.
3. The control plane validates and queues the event.
4. An isolated worker obtains the minimum required repository access.
5. Deterministic context is collected.
6. Rules and analysis workflows run.
7. The worker creates validated `.trace` artifacts.
8. Approved outputs are committed, attached to the PR, or stored for user approval according to project policy.
9. The dashboard indexes and displays the result.

### Requirements

- short-lived repository credentials;
- tenant isolation;
- explicit retention controls;
- idempotent webhook processing;
- retry-safe jobs;
- audit logs;
- clear source-code handling policy.

## 4.2 Local mode

### Flow

1. The user installs the TRACE CLI and optional Agent Skill.
2. The CLI detects repository state and `.trace/config.yml`.
3. The user or agent invokes a workflow.
4. All repository parsing and evidence collection occurs locally.
5. The configured model runs through BYOK, a local model, or an approved endpoint.
6. Artifacts are validated and written into `.trace/`.
7. Nothing is synchronized unless the user explicitly enables and approves sync.

### Requirements

- no required TRACE Cloud account for core artifact generation;
- offline-capable deterministic analysis;
- explicit logs showing any data sent to a model endpoint;
- predictable configuration;
- cross-platform behavior;
- non-destructive writes.

## 4.3 Hybrid mode

### Flow

1. Analysis runs locally or inside the customer’s CI/VPC.
2. The local runtime creates valid `.trace` artifacts.
3. A sync policy determines which artifacts and fields are eligible for upload.
4. The user or automation approves synchronization.
5. TRACE Cloud validates and indexes the uploaded artifacts.
6. The dashboard provides centralized reporting without receiving the source repository.

### Requirements

- field-level or artifact-level sync controls;
- redaction before network transfer;
- signed source identity or execution provenance;
- conflict handling for local and cloud edits;
- transparent upload preview;
- deletion and resynchronization behavior.

# 5. Repository structure and artifact model

The structure below is a proposed MVP contract. The final specification must be independently versioned and documented.

```text
.trace/
├── config.yml
├── README.md
├── schema-version
├── rules/
│   ├── project.md
│   └── architecture.md
├── reports/
│   ├── daily/
│   │   └── 2026/
│   │       └── 08/
│   │           └── 2026-08-04.md
│   └── weekly/
├── pull-requests/
│   └── 142.md
├── decisions/
│   └── DEC-2026-0042.md
├── risks/
│   └── RISK-2026-0017.md
├── debt/
│   └── DEBT-2026-0008.md
├── state/
│   ├── open-prs.json
│   └── sync.json
└── indexes/
    └── artifacts.json
```

## 5.1 Human-readable artifacts

Markdown should be used for durable records that humans are expected to review:

- daily and weekly reports;
- PR briefs;
- decisions;
- risks;
- technical-debt records;
- project and architecture rules.

Markdown artifacts should use structured front matter for machine-readable metadata.

## 5.2 Machine-readable artifacts

JSON or YAML should be used for:

- configuration;
- indexes;
- local runtime state;
- sync state;
- graph snapshots or references;
- validation metadata.

Generated indexes should be reproducible and should not be treated as authoritative when they can be rebuilt from durable records.

## 5.3 Required artifact metadata

Each durable artifact should contain, at minimum:

- `schema_version`;
- stable `id`;
- `artifact_type`;
- creation and update timestamps;
- repository identity;
- source branch or base/head references where relevant;
- generator identity and version;
- execution origin: `cloud`, `local`, `ci`, or `third_party`;
- evidence references;
- confidence classification where inference is present;
- review status;
- supersession links where applicable;
- sensitivity and sync policy metadata.

## 5.4 Stable identifiers

Artifacts must use stable identifiers that do not depend on file position.

Examples:

- `DEC-2026-0042`
- `RISK-2026-0017`
- `PR-GITHUB-142`
- `REPORT-DAILY-2026-08-04`

A renamed or moved file must retain the same identifier.

## 5.5 Append and supersede behavior

Historical reports should not be silently rewritten.

Durable records should prefer:

- append-only history;
- explicit amendments;
- supersession links;
- review status transitions.

Indexes may be regenerated. Historical evidence should remain inspectable.

# 6. Evidence and provenance model

TRACE needs an evidence graph, even if the MVP stores it in relational tables and artifact references rather than a dedicated graph database.

## 6.1 Evidence types

Potential evidence nodes include:

- repository;
- branch;
- commit;
- pull request;
- changed file;
- code symbol;
- issue or task;
- acceptance criterion;
- test result;
- CI check;
- team rule;
- ownership entry;
- decision;
- risk;
- debt item;
- release;
- incident;
- model-generated finding.

## 6.2 Relationships

Examples:

- PR implements Issue
- Commit belongs to PR
- Change modifies Symbol
- Symbol depends on Symbol
- Rule applies to Component
- Finding supported by Evidence
- Decision governs Component
- PR conflicts with PR
- Risk introduced by Change
- Test verifies Acceptance Criterion
- Artifact supersedes Artifact

## 6.3 Finding classifications

Every finding should be classified as one of:

- **Deterministic:** directly produced by a rule or observable state
- **Correlated:** derived by connecting multiple deterministic facts
- **Semantic:** produced through language-model interpretation
- **Uncertain:** plausible but insufficiently supported

The UI and artifact format must preserve this distinction.

## 6.4 Human disposition

Reviewers should be able to:

- accept;
- reject;
- mark as intentional;
- request clarification;
- resolve;
- suppress under a scoped rule;
- edit and approve a durable record.

Disposition becomes future context, but should not be blindly treated as a universal rule.

# 7. Change-analysis pipeline

The analysis pipeline should be staged to reduce cost, latency, and hallucination.

## Stage 1 — Event normalization

Convert GitHub events, local commands, and scheduled runs into a common internal job shape.

The event should include:

- repository identity;
- trigger type;
- base and head references;
- relevant PR or commit identifiers;
- organization and policy context;
- requested output types;
- execution mode.

## Stage 2 — Change-set construction

Build the exact set of relevant changes:

- commits in range;
- changed files;
- additions, modifications, deletions, and renames;
- changed symbols;
- related open PRs;
- linked issues;
- CI and test state.

## Stage 3 — Deterministic enrichment

Collect facts before model use:

- language and framework detection;
- dependency changes;
- ownership;
- schema or migration changes;
- public API changes;
- component boundaries;
- existing rules;
- previous decisions and risks;
- relevant historical artifacts.

## Stage 4 — Context selection

Select only the context required for the requested analysis.

The selector should prefer:

- changed symbols and direct dependents;
- rules applying to affected components;
- linked requirements;
- recent relevant decisions;
- active PRs touching related surfaces;
- accepted/rejected historical findings with direct relevance.

It should avoid sending the entire repository or entire `.trace` history to a model.

## Stage 5 — Deterministic checks

Run configured checks such as:

- missing tests;
- failed CI;
- protected area modification;
- migration ordering;
- ownership requirements;
- dependency-policy violations;
- artifact schema validation;
- overlap with open work.

## Stage 6 — Semantic reasoning

Use the model for tasks that require interpretation:

- summarize the semantic change;
- compare implementation to stated intent;
- identify conceptual conflicts;
- explain impact;
- propose decision or risk records;
- classify incomplete work;
- produce role-specific narratives.

Model output must conform to a structured response contract before artifact generation.

## Stage 7 — Verification and deduplication

Before surfacing a finding:

- verify referenced evidence exists;
- remove duplicates;
- collapse related findings;
- filter low-priority style observations;
- compare against suppressions and prior dispositions;
- downgrade unsupported certainty;
- enforce output limits.

## Stage 8 — Artifact generation

Produce Markdown and metadata from validated structured results.

The model should not directly write arbitrary repository files without schema validation and path restrictions.

## Stage 9 — Policy-controlled delivery

According to project policy, TRACE may:

- write artifacts locally;
- prepare a commit for approval;
- publish a PR summary;
- add a small number of inline comments;
- request a human reviewer;
- synchronize approved metadata;
- withhold uncertain findings from public PR comments.

# 8. Codebase understanding

## 8.1 MVP approach

The MVP should use structural parsing and a lightweight dependency graph rather than relying only on vector similarity.

The initial graph should model:

- files;
- symbols;
- imports;
- calls where practical;
- inheritance or implementation relationships;
- package/module boundaries;
- known components;
- ownership;
- schema and API surfaces.

## 8.2 Storage approach

A dedicated graph database is not required for the MVP.

The graph can initially be stored using:

- normalized relational tables;
- adjacency records;
- content-addressed snapshots;
- rebuildable local indexes.

A specialized graph system should be introduced only if measured queries and scale justify it.

## 8.3 Language support

The first implementation should support a narrow, explicit language set.

Each language adapter must define:

- parser;
- symbol extraction;
- import/dependency extraction;
- test-file detection;
- API/schema conventions;
- confidence limitations.

Unsupported languages should fall back to file-level analysis rather than pretending to have symbol-level precision.

# 9. Concurrent-change conflict detection

Conflict detection is a core differentiator and should combine deterministic and semantic methods.

## 9.1 Deterministic conflict signals

- same file changed by multiple open PRs;
- same symbol changed;
- overlapping database migration scope;
- incompatible dependency versions;
- shared API or schema changes;
- rename/delete conflicts;
- dependency ordering requirements;
- duplicate ownership-sensitive changes;
- test fixtures or contracts modified concurrently.

## 9.2 Semantic conflict signals

- different implementations of the same requirement;
- conflicting acceptance criteria;
- incompatible architectural assumptions;
- duplicated feature work;
- one PR depending on behavior removed by another;
- conflicting security or authorization models;
- release sequencing risk;
- contradictory decisions.

## 9.3 Conflict output

A conflict record should include:

- involved changes;
- affected components;
- deterministic overlap evidence;
- semantic explanation;
- severity;
- confidence classification;
- recommended owner or coordination group;
- required sequencing or decision;
- resolution status.

TRACE must not present semantic conflict detection as certainty when only weak evidence exists.

# 10. Reports

## 10.1 PR brief

A PR brief should contain:

- stated intent;
- semantic summary;
- affected components and owners;
- requirement coverage;
- deterministic findings;
- semantic risks;
- concurrent-change conflicts;
- missing evidence or incomplete work;
- proposed updates to decisions, risks, or debt;
- recommended human action;
- evidence links.

## 10.2 Daily report

A daily report should summarize changes in a fixed time window and explain:

- what materially changed;
- why it changed;
- which goals moved;
- which decisions or risks changed;
- which teams or components are affected;
- which active conflicts exist;
- what remains incomplete;
- what needs attention next.

## 10.3 Weekly report

A weekly report should emphasize coordination and direction rather than raw activity:

- completed and active outcomes;
- requirement progress;
- conflict and dependency trends;
- decision, risk, and debt movement;
- blocked work;
- repeated governance problems;
- high-priority next actions.

## 10.4 Report constraints

Reports must:

- avoid repeating the full Git log;
- distinguish facts from interpretation;
- provide links to evidence;
- remain concise enough to read;
- exclude individual productivity scoring;
- indicate missing context;
- show generation and review status.

# 11. Rules and governance

## 11.1 Rule types

TRACE should support:

- deterministic configuration rules;
- natural-language guidance;
- component-specific rules;
- organization-level policies;
- report-delivery rules;
- data-sharing and sync policies;
- human-approval requirements.

## 11.2 Rule precedence

Rule scope must be explicit.

A possible precedence model:

1. organization mandatory policy;
2. repository policy;
3. component or path policy;
4. workflow-specific instruction;
5. user-requested analysis options.

Lower scopes cannot silently disable mandatory higher-scope policies.

## 11.3 Rule explainability

Every policy result must show:

- rule identifier;
- rule scope;
- evidence evaluated;
- result;
- severity;
- permitted actions;
- override authority;
- override reason where used.

Natural-language rules must not be treated as deterministic unless they are compiled into an explicit check.

# 12. GitHub integration

GitHub is the first supported Git provider.

## 12.1 GitHub App responsibilities

- repository installation and permission management;
- webhook delivery;
- reading PRs, commits, issues, checks, and repository metadata;
- publishing comments or checks when allowed;
- committing or proposing `.trace` updates according to policy.

## 12.2 Required webhook handling

Initial events should include:

- installation changes;
- repository changes;
- pull request opened, reopened, synchronized, closed, and merged;
- issue linkage changes where available;
- check-suite/check-run completion;
- push events for configured branches;
- manual commands or review requests.

## 12.3 Webhook requirements

- signature validation;
- delivery-ID deduplication;
- idempotent processing;
- fast acknowledgement;
- asynchronous analysis;
- event replay support;
- dead-letter handling;
- installation permission checks.

# 13. Dashboard architecture

The dashboard reads indexed artifact data and operational state.

## 13.1 Primary views

- organization and repository overview;
- change timeline;
- PR intelligence view;
- active conflict queue;
- decisions, risks, and debt timeline;
- daily and weekly reports;
- rules and governance configuration;
- sync and execution history;
- artifact viewer with evidence links;
- approval and disposition workflow.

## 13.2 Source-of-truth behavior

The dashboard database is an operational index.

When a durable artifact exists in `.trace`, the dashboard should preserve:

- repository path;
- blob or commit reference;
- artifact checksum;
- sync state;
- local/cloud origin;
- divergence state.

Dashboard edits to durable records must either create an explicit repository update or remain clearly marked as a pending overlay.

## 13.3 Real-time behavior

The MVP does not require full collaborative real-time editing.

Near-real-time status updates are sufficient for:

- job progress;
- webhook state;
- report readiness;
- conflict alerts;
- review disposition.

# 14. Data model

The operational data model should include the following top-level entities:

- User
- Organization
- Membership
- Repository
- GitInstallation
- RuleSet
- AnalysisRun
- Artifact
- EvidenceReference
- Finding
- FindingDisposition
- PullRequestSnapshot
- ChangeSet
- Component
- Ownership
- Conflict
- SyncTarget
- SyncEvent
- ModelInvocation
- AuditEvent

## 14.1 Tenant isolation

Every organization-owned entity must be tenant-scoped.

Authorization checks must occur at the data-access layer, not only in the UI.

## 14.2 Artifact identity

The cloud database should store metadata and searchable projections of artifacts, while retaining a reference to the repository artifact and checksum.

## 14.3 Sensitive data minimization

The system should avoid storing raw source code in the primary application database.

Temporary analysis data must have explicit retention behavior and should be isolated from long-lived metadata.

---

# 15. Model-provider architecture

TRACE should not depend on one model provider.

## 15.1 Provider abstraction

The runtime should support a common interface for:

- structured generation;
- tool or context limits;
- model capability metadata;
- token and cost reporting;
- retries and timeout behavior;
- data-retention classification;
- local endpoints.

## 15.2 BYOK

Local and enterprise modes should support customer-managed credentials.

Credentials must never be written to `.trace`.

## 15.3 Structured output

Model output must validate against a schema before it can create findings or artifacts.

Invalid output should be retried with bounded attempts and then fail visibly rather than creating malformed records.

## 15.4 Context logging

Where policy allows, TRACE should record a safe manifest of what evidence categories were sent to a model.

It should not duplicate sensitive source content in audit logs.

# 16. Security and privacy

## 16.1 Minimum security requirements

- least-privilege GitHub App permissions;
- encrypted credentials and tokens;
- short-lived installation access tokens;
- verified webhook signatures;
- tenant isolation;
- audit logging for sensitive actions;
- secret scanning for `.trace` output;
- path allowlists for generated files;
- model-provider data handling visibility;
- deletion and retention controls;
- protected branch awareness;
- rate limiting and abuse protection.

## 16.2 Untrusted repository content

Repository files, issue text, PR descriptions, comments, and existing `.trace` artifacts must be treated as untrusted input.

The system must defend against:

- prompt injection;
- instructions embedded in source comments;
- malicious Markdown;
- path traversal;
- generated secret exfiltration;
- command injection;
- unsafe test or build execution;
- poisoned memory artifacts.

## 16.3 Execution sandbox

Cloud workers must not execute arbitrary repository commands by default.

Any build or test execution must occur in an isolated sandbox with:

- explicit policy;
- network controls;
- resource limits;
- timeouts;
- non-root execution;
- temporary credentials;
- destroyed workspace after completion.

## 16.4 Artifact safety

Before committing or syncing an artifact:

- validate schema;
- validate path;
- scan for secrets;
- apply redaction rules;
- enforce size limits;
- reject binary or executable content;
- record checksum and generator provenance.

---

# 17. Reliability and observability

## 17.1 Idempotency

Every incoming event and analysis workflow must have a stable idempotency key.

Repeated webhook deliveries must not create duplicate artifacts or comments.

## 17.2 Job state

Analysis runs should move through explicit states:

- queued;
- collecting;
- analyzing;
- validating;
- awaiting approval;
- publishing;
- completed;
- failed;
- cancelled.

## 17.3 Observability

The platform should track:

- analysis latency;
- queue delay;
- model cost and token usage;
- context size;
- artifact validation failures;
- finding acceptance and rejection;
- duplicate suppression;
- webhook failure rate;
- sync divergence;
- conflict-warning accuracy;
- report readership and action rate.

The system should not optimize for number of findings produced.

# 18. Recommended implementation architecture

The reference implementation should use a TypeScript-centered monorepo for shared schemas and end-to-end type safety.

A practical high-level structure:

```text
apps/
├── web/                 # Dashboard and product web application
├── api/                 # Public API and GitHub webhook receiver
└── worker/              # Background analysis and synchronization jobs

packages/
├── trace-schema/        # Artifact schemas and validators
├── trace-core/          # Shared domain logic
├── trace-cli/           # Local CLI runtime
├── trace-github/        # GitHub integration
├── trace-analysis/      # Change analysis pipeline
├── trace-rules/         # Rule loading and evaluation
├── trace-models/        # Model-provider abstraction
├── trace-ui/            # Shared design-system components
└── trace-config/        # Shared configuration
```

Recommended infrastructure categories:

- PostgreSQL for transactional and indexed metadata;
- a durable background-job queue;
- isolated container workers for cloud analysis;
- S3-compatible object storage only where repository artifacts are insufficient;
- GitHub App authentication for repository access;
- standard telemetry for logs, metrics, and traces;
- schema validation shared by CLI, API, worker, and dashboard.

The initial implementation should avoid introducing a graph database, vector database, event-streaming platform, or microservice fleet until real workload measurements require them.

# 19. MVP scope

## 19.1 Included

The first usable TRACE release should provide:

- GitHub App installation;
- one-organization and multi-repository account model;
- local CLI and initial Agent Skill;
- versioned `.trace` specification;
- PR and recent-commit ingestion;
- deterministic change-set construction;
- limited symbol and dependency extraction for supported languages;
- concise PR brief;
- daily report generation;
- issue/goal linkage from GitHub Issues and PR metadata;
- same-file, same-symbol, API/schema, migration, and semantic conflict detection;
- team-defined repository rules;
- evidence-backed findings;
- human disposition workflow;
- minimal dashboard;
- hybrid artifact synchronization;
- audit trail and privacy controls;
- no individual scoring.

## 19.2 Explicitly excluded

The MVP should not include:

- a general-purpose coding agent;
- automated code fixes;
- automatic merge approval;
- a full security-scanning platform;
- a full static-analysis engine;
- DORA or finance-oriented executive analytics;
- developer productivity ranking;
- IDE extensions;
- GitLab, Bitbucket, or Azure DevOps support;
- arbitrary CI command execution;
- organization-wide architecture discovery across every language;
- complex real-time collaboration;
- a dedicated graph database;
- a proprietary-only artifact format.

# 21. Acceptance qualities for the product

The implementation is not successful merely because it generates text.

TRACE must meet these qualities:

## Trust

- findings cite evidence;
- uncertainty is visible;
- users can reject and correct output;
- historical records are not silently rewritten.

## Portability

- local artifacts remain useful without the cloud service;
- artifacts validate against a public schema;
- different execution modes produce compatible output.

## Privacy

- local mode works without source-code upload;
- sync is explicit and inspectable;
- credentials never enter artifacts.

## Signal quality

- duplicate and low-priority findings are suppressed;
- deterministic checks precede semantic speculation;
- output limits protect reviewer attention.

## Operational reliability

- webhook processing is idempotent;
- jobs are retry-safe;
- failures are visible;
- artifact writes are non-destructive.

## Developer acceptance

- the system does not score individuals;
- reports are concise;
- findings are actionable;
- setup does not require replacing existing tools.

# 22. Final technical positioning

TRACE should be implemented as:

> **A repository-native, local-first change-intelligence and governance platform with a shared open artifact contract, deterministic evidence collection, selective AI reasoning, concurrent-change analysis, and an optional cloud control plane.**

AI review is one capability inside TRACE. It is not the complete product.

The durable technical advantage is the combination of:

- portable `.trace` artifacts;
- evidence and provenance;
- local/cloud compatibility;
- active-work conflict detection;
- decision and risk continuity;
- policy-controlled coordination;
- high-signal output instead of comment volume.

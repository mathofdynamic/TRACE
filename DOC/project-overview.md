# Trace چیست؟

## معرفی کوتاه

**Trace یک سیستم هوشمند برای بررسی، ثبت و مدیریت تغییرات پروژه‌های نرم‌افزاری است.**

Trace تغییرات ایجادشده توسط برنامه‌نویسان یا عامل‌های هوش مصنوعی را بررسی می‌کند و آن‌ها را به گزارش‌های قابل‌فهم و قابل‌اقدام تبدیل می‌کند.

این گزارش‌ها براساس قوانین و انتظارات هر تیم تولید می‌شوند و می‌توانند برای برنامه‌نویس، اعضای تیم، مدیر پروژه یا رهبر فنی خروجی‌های متفاوتی داشته باشند.

Trace می‌تواند به دو شکل اصلی اجرا شود:

* به‌صورت ابری توسط سرویس Trace
* به‌صورت محلی از طریق Trace Skill داخل پروژه

همچنین کاربر می‌تواند از مدل ترکیبی استفاده کند؛ یعنی تحلیل در محیط محلی انجام شود و فقط گزارش‌های نهایی در داشبورد Trace مدیریت شوند.

---

## مشکلی که Trace حل می‌کند

هوش مصنوعی سرعت تولید کد را افزایش داده است.

یک برنامه‌نویس اکنون می‌تواند در زمان کمتری کد بیشتری تولید کند. عامل‌های هوش مصنوعی نیز می‌توانند هم‌زمان روی چند بخش از یک پروژه کار کنند.

در نتیجه، تعداد Commitها، Pull Requestها و تغییرات روزانه پروژه افزایش پیدا می‌کند.

اما توان مدیران و برنامه‌نویسان ارشد برای بررسی، فهم و مستندسازی این تغییرات با همان سرعت افزایش پیدا نمی‌کند.

این مسئله مشکلات مختلفی ایجاد می‌کند:

* بررسی دستی حجم زیادی از تغییرات زمان‌بر است
* اعضای تیم نمی‌دانند دیگران دقیقاً چه کاری انجام داده‌اند
* دلیل بعضی تغییرات بعد از مدتی فراموش می‌شود
* تصمیم‌های مهم میان Commitها، Pull Requestها و پیام‌های تیم پراکنده می‌شوند
* کدهای ناسازگار یا ناقص ممکن است وارد پروژه شوند
* چند فرد یا Agent ممکن است هم‌زمان تصمیم‌های متناقض بگیرند
* مشخص نیست یک تغییر واقعاً به هدف موردنظر رسیده است یا نه
* ورود افراد یا Agentهای جدید به پروژه دشوار می‌شود
* مدیر برای فهم وضعیت پروژه مجبور به بررسی تعداد زیادی تغییر فنی می‌شود

Git نشان می‌دهد چه فایل‌ها و خطوطی تغییر کرده‌اند، اما معمولاً توضیح نمی‌دهد:

* چرا این تغییر انجام شده است
* هدف آن چه بوده است
* چه اثری روی پروژه دارد
* چه ریسک‌هایی ایجاد می‌کند
* چه تصمیمی پشت آن بوده است
* چه کاری هنوز باقی مانده است

Trace این فاصله را پوشش می‌دهد.

---

## Trace چگونه کار می‌کند؟

مدیر، رهبر فنی یا مالک پروژه مشخص می‌کند که تغییرات براساس چه قوانین و انتظاراتی بررسی شوند.

این قوانین می‌توانند برای هر پروژه یا بخش از پروژه متفاوت باشند.

برای مثال، Trace می‌تواند بررسی کند:

* هدف تغییر چه بوده است
* چرا تغییر انجام شده است
* آیا نتیجه با هدف اعلام‌شده مطابقت دارد
* آیا احتمال ایجاد خطا وجود دارد
* آیا استانداردهای تیم رعایت شده‌اند
* چه بخش‌هایی از پروژه تحت تأثیر قرار گرفته‌اند
* آیا تغییر با ساختار فعلی پروژه سازگار است
* آیا با تغییرات دیگر تداخل دارد
* آیا کار کامل شده یا هنوز بخش‌هایی باقی مانده است
* آیا نیاز به بررسی انسانی وجود دارد
* چه فردی باید تغییر را بررسی کند
* آیا تصمیم مهمی گرفته شده که باید ثبت شود

Trace سپس تغییرات پروژه را تحلیل می‌کند و خروجی‌های لازم را در ساختاری استاندارد داخل پوشه `.trace` قرار می‌دهد.

---

# پوشه `.trace`

Trace در ریشه پروژه یک پوشه مخفی با نام `.trace` ایجاد می‌کند.

این پوشه محل اصلی تمام خروجی‌های قابل‌حمل و قابل‌بررسی Trace است.

فرقی نمی‌کند تحلیل توسط سرویس ابری Trace انجام شده باشد یا توسط Skill محلی؛ خروجی نهایی باید در ساختار استاندارد `.trace` قرار گیرد.

یک ساختار نمونه:

```text
.trace/
├── config.yml
├── rules/
├── reports/
│   └── 2026/
│       ├── August/
│       │   ├── 2026-08-03.md
│       │   └── 2026-08-04.md
│       └── September/
├── pull-requests/
├── decisions/
├── risks/
└── index.json
```

ساختار دقیق ممکن است با توسعه محصول تغییر کند، اما اصل اصلی ثابت است:

> تمام خروجی‌های مهم Trace باید داخل پروژه، در ساختاری مشخص و قابل‌خواندن نگه‌داری شوند.

---

## گزارش‌های روزانه

Trace تغییرات پروژه را در بازه‌های ۲۴ ساعته بررسی می‌کند.

اگر در این مدت تغییری وجود داشته باشد، یک گزارش روزانه در پوشه ماه مربوط ایجاد می‌شود.

برای مثال:

```text
.trace/reports/2026/August/2026-08-04.md
```

اگر در آن روز تغییری وجود نداشته باشد، نیازی به ساخت گزارش خالی نیست.

هر گزارش باید توضیح دهد:

* چه تغییراتی انجام شده‌اند
* چه قابلیت‌هایی اضافه، حذف یا اصلاح شده‌اند
* چه فرد یا Agentی تغییرات را ایجاد کرده است
* هدف تغییرات چه بوده است
* چرا تغییرات انجام شده‌اند
* تغییرات به کدام Task، Issue یا Pull Request مربوط هستند
* چه بخش‌هایی از پروژه تحت تأثیر قرار گرفته‌اند
* نتیجه واقعی تغییر چه بوده است
* آیا نتیجه با هدف اولیه مطابقت دارد
* چه مشکلات یا ریسک‌هایی شناسایی شده‌اند
* چه تصمیم‌هایی گرفته شده‌اند
* چه کارهایی هنوز باقی مانده‌اند
* آیا تغییرات روی کار دیگر اعضای تیم اثر می‌گذارند
* آیا با تغییرات دیگر تداخل یا تناقضی وجود دارد
* اقدام بعدی پیشنهادی چیست

این گزارش نباید فقط فهرستی از Commitها یا فایل‌های تغییرکرده باشد.

Trace باید تغییرات فنی را به توضیحی قابل‌فهم درباره اتفاق واقعی پروژه تبدیل کند.

---

## تمام خروجی‌های Trace در یک محل

پوشه `.trace` فقط برای گزارش‌های روزانه نیست.

تمام خروجی‌های قابل‌ممیزی Trace می‌توانند داخل آن قرار بگیرند، از جمله:

* گزارش‌های روزانه
* خلاصه Pull Requestها
* نتایج بررسی کد
* ریسک‌های شناسایی‌شده
* تصمیم‌های مهم پروژه
* قوانین و استانداردهای تیم
* ارتباط میان تغییرات، Issues و Tasks
* کارهای باقی‌مانده
* هشدارهای مربوط به تداخل تغییرات
* اطلاعات لازم برای نمایش در داشبورد

با این روش، اطلاعات پروژه میان چند سرویس و ابزار مختلف پراکنده نمی‌شود.

`.trace` به محل استاندارد نگه‌داری دانش تولیدشده توسط Trace تبدیل می‌شود.

---

## چه اطلاعاتی نباید در `.trace` ذخیره شوند؟

تمام خروجی‌های مفید Trace می‌توانند در `.trace` قرار بگیرند، اما اطلاعات حساس یا موقت نباید داخل آن ذخیره شوند.

مواردی مانند این‌ها نباید در `.trace` قرار گیرند:

* API Key
* رمز عبور
* Tokenهای GitHub
* اطلاعات ورود
* فایل‌های موقت
* Cacheهای بزرگ
* داده‌های داخلی سرویس ابری
* اطلاعات محرمانه غیرضروری
* داده‌هایی که برای فهم یا بررسی پروژه کاربردی ندارند

پوشه `.trace` باید قابل‌حمل، قابل‌خواندن و امن باقی بماند.

---

# روش‌های استفاده از Trace

## ۱. Trace Cloud

در این حالت، کاربر Repository خود را به سرویس Trace متصل می‌کند.

Trace Cloud وظایف زیر را انجام می‌دهد:

* بررسی تغییرات
* تحلیل Commitها و Pull Requestها
* اجرای قوانین تیم
* تولید گزارش‌های روزانه
* شناسایی ریسک‌ها و تداخل‌ها
* ثبت Comment روی Pull Request
* مدیریت گزارش‌ها در داشبورد
* ایجاد یا به‌روزرسانی فایل‌های `.trace`

این حالت برای تیم‌هایی مناسب است که می‌خواهند فرایند بررسی و گزارش‌گیری به‌صورت خودکار توسط Trace مدیریت شود.

---

## ۲. Trace Skill

کاربر می‌تواند Trace Skill را دریافت کرده و به پروژه خود اضافه کند.

این Skill می‌تواند توسط Coding Agentها یا ابزارهایی مانند Claude Code، Codex، Cursor و سایر محیط‌های مشابه اجرا شود.

در این حالت:

* کد داخل محیط خود کاربر باقی می‌ماند
* تحلیل با مدل و زیرساخت انتخابی کاربر انجام می‌شود
* Trace Skill تغییرات را بررسی می‌کند
* خروجی‌ها را براساس استاندارد Trace تولید می‌کند
* فایل‌ها را داخل `.trace` قرار می‌دهد

این حالت برای پروژه‌های شخصی، خصوصی یا سازمان‌هایی مناسب است که نمی‌خواهند کدشان برای تحلیل به سرویس خارجی ارسال شود.

---

## ۳. حالت Hybrid

در حالت Hybrid، تحلیل در محیط محلی کاربر انجام می‌شود، اما خروجی‌های `.trace` در داشبورد Trace نمایش و مدیریت می‌شوند.

در این مدل:

* کد اصلی می‌تواند در محیط خصوصی باقی بماند
* Trace Skill گزارش‌ها را محلی تولید می‌کند
* فقط خروجی‌های انتخاب‌شده با داشبورد همگام می‌شوند
* مدیر می‌تواند گزارش چند پروژه یا چند تیم را در یک محل مشاهده کند

این حالت برای شرکت‌هایی مناسب است که هم به حفظ حریم خصوصی نیاز دارند و هم داشبورد مدیریتی مرکزی می‌خواهند.

---

# داشبورد Trace

داشبورد Trace باید بتواند خروجی‌های تولیدشده در هر سه حالت Cloud، Local و Hybrid را مدیریت کند.

کاربر می‌تواند در داشبورد ببیند:

* تغییرات اخیر پروژه
* گزارش‌های روزانه
* Pull Requestهای بررسی‌شده
* ریسک‌های مهم
* تصمیم‌های ثبت‌شده
* تغییرات پرریسک
* تداخل میان فعالیت اعضای تیم یا Agentها
* کارهای ناقص
* وضعیت کلی پروژه
* گزارش فعالیت هر بخش یا فرد
* روند تغییرات در بازه‌های زمانی مختلف

داشبورد نباید تنها منبع اطلاعات باشد.

اطلاعات اصلی باید در `.trace` باقی بمانند و داشبورد نقش نمایش، مدیریت، جست‌وجو و هماهنگی را داشته باشد.

---

# خروجی برای برنامه‌نویس

Trace به برنامه‌نویس کمک می‌کند متوجه شود:

* چه کاری انجام داده است
* کدام بخش‌ها درست اجرا شده‌اند
* چه مشکلات یا ریسک‌هایی وجود دارند
* کدام استانداردها رعایت نشده‌اند
* چه مواردی باید اصلاح شوند
* تغییرات او چه اثری روی پروژه دارند
* آیا نتیجه با هدف اولیه مطابقت دارد
* چه تصمیم‌هایی باید برای آینده ثبت شوند

این خروجی باید بازخوردی عملی باشد، نه صرفاً یک امتیاز کلی.

---

# خروجی برای تیم

اعضای تیم می‌توانند ببینند:

* در هر بخش پروژه چه اتفاقی افتاده است
* دیگران روی چه موضوعاتی کار کرده‌اند
* چه قابلیت‌هایی تغییر کرده‌اند
* چه تصمیم‌هایی گرفته شده‌اند
* چه کارهایی کامل یا ناقص هستند
* چه تغییراتی روی فعالیت سایر افراد اثر می‌گذارند
* آیا میان چند تغییر تداخل یا تناقض وجود دارد
* چه موضوعاتی نیازمند هماهنگی بیشتر هستند

هدف این بخش جلوگیری از دوباره‌کاری و تصمیم‌های متناقض است.

---

# خروجی برای مدیر

مدیر یا رهبر فنی می‌تواند ببیند:

* در یک بازه زمانی چه تغییراتی انجام شده‌اند
* هر فرد یا تیم روی چه بخشی کار کرده است
* هدف هر تغییر چه بوده است
* نتیجه واقعی هر تغییر چیست
* کدام تغییرات پرریسک هستند
* چه مواردی نیازمند بررسی انسانی هستند
* آیا قوانین تیم رعایت شده‌اند
* چه مشکلاتی مرتب تکرار می‌شوند
* آیا چند تیم یا Agent در مسیرهای متناقض حرکت می‌کنند
* وضعیت کلی پیشرفت و سلامت پروژه چگونه است

مدیر می‌تواند نحوه بررسی و گزارش‌گیری را براساس نیاز خود تنظیم کند.

---

# تعامل با Pull Requestها

Trace می‌تواند Pull Requestها را بررسی کرده و در صورت نیاز:

* خلاصه تغییرات را تولید کند
* هدف تغییر را توضیح دهد
* مشکلات احتمالی را اعلام کند
* پیشنهاد اصلاحی ارائه دهد
* سؤالات لازم را مطرح کند
* تداخل با Pull Requestهای دیگر را شناسایی کند
* موارد مهم را برای بررسی انسانی مشخص کند
* Reviewer مناسب را پیشنهاد دهد
* نتیجه بررسی را به‌صورت Comment ثبت کند
* مشخص کند آیا تغییر برای ادغام آماده است یا نه
* گزارش نهایی را داخل `.trace` ذخیره کند

Trace نباید برای هر تغییر کوچک Commentهای متعدد و غیرضروری ایجاد کند.

تمرکز آن باید روی مسائل مهم، قابل‌اثبات و قابل‌اقدام باشد.

---

# قوانین اختصاصی هر تیم

هر تیم استانداردها، ساختار و اولویت‌های مخصوص خود را دارد.

مدیر می‌تواند مشخص کند:

* چه چیزی برای پروژه مهم است
* چه تغییراتی حساس محسوب می‌شوند
* چه استانداردهایی باید رعایت شوند
* چه بخش‌هایی نیازمند بررسی دقیق‌تر هستند
* چه نوع گزارشی تولید شود
* چه مواردی نیازمند هشدار هستند
* چه شرایطی نیاز به بررسی انسانی دارند
* چه اطلاعاتی باید در `.trace` ذخیره شوند
* چه خروجی‌هایی اجازه همگام‌سازی با Cloud را دارند

بنابراین Trace براساس روش مدیریت و قوانین هر تیم عمل می‌کند، نه یک مجموعه قانون ثابت برای همه.

# تفاوت Git با Trace

Git تاریخچه فنی کد را نگه‌داری می‌کند:

* چه فایلی تغییر کرده است
* چه خطوطی اضافه یا حذف شده‌اند
* چه کسی Commit زده است
* تغییر چه زمانی انجام شده است

Trace تاریخچه قابل‌فهم پروژه را نگه‌داری می‌کند:

* چه اتفاقی افتاده است
* چرا تغییر انجام شده است
* هدف تغییر چه بوده است
* نتیجه چه شده است
* چه ریسک‌هایی وجود دارند
* چه تصمیمی گرفته شده است
* چه کاری هنوز باقی مانده است
* تغییر چه ارتباطی با بخش‌های دیگر دارد

**Git تاریخچه کد است؛ Trace تاریخچه فهم پروژه است.**

---

# چیزی که Trace نیست

Trace ابزار تولید کد نیست.

Trace فقط یک ربات پیدا کردن خطا نیست.

Trace فقط یک ابزار خلاصه‌سازی Pull Request نیست.

Trace نباید عملکرد افراد را فقط براساس تعداد Commit، حجم کد یا تعداد Pull Request ارزیابی کند.

تمرکز Trace باید روی این موارد باشد:

* کیفیت تغییرات
* سلامت پروژه
* هماهنگی تیم
* حفظ تصمیم‌ها
* کاهش ریسک

# کاربران اصلی Trace

Trace برای گروه‌های زیر طراحی می‌شود:

* مدیران پروژه‌های نرم‌افزاری
* رهبران فنی
* برنامه‌نویسان ارشد
* تیم‌های توسعه نرم‌افزار
* تیم‌های استفاده‌کننده از Coding Agentها
* شرکت‌های دارای پروژه‌های خصوصی
* شرکت‌های دارای برنامه‌نویسان دورکار
* آژانس‌های مدیریت‌کننده چند پروژه
* تیم‌هایی با حجم زیاد تغییرات کد
* سازمان‌هایی که حفظ دانش پروژه برای آن‌ها مهم است

---

# اهداف اصلی Trace

## ۱. کمک به برنامه‌نویس

برنامه‌نویس بفهمد چه کاری انجام داده، نتیجه آن چه بوده و چه مواردی باید اصلاح شوند.

## ۲. هماهنگی تیم

اعضای تیم بدانند دیگران چه کاری انجام داده‌اند و تغییرات مختلف چه ارتباط یا تداخلی با یکدیگر دارند.

## ۳. کنترل و دید مدیریتی

مدیر بتواند وضعیت پروژه را براساس قوانین و استانداردهای خود بررسی کند، بدون اینکه مجبور باشد تمام Commitها و Pull Requestها را به‌صورت دستی بخواند.

## ۴. حفظ دانش پروژه

دلیل تغییرات، تصمیم‌ها، ریسک‌ها و روند توسعه پروژه در ساختار `.trace` ثبت شوند و در طول زمان از بین نروند.

## ۵. استقلال در نحوه اجرا

کاربر بتواند Trace را به‌صورت Cloud، Local یا Hybrid استفاده کند و برای استفاده از ساختار Trace مجبور به ارسال کد خود به سرویس ابری نباشد.

# هدف نهایی

هدف Trace این است که با افزایش سرعت تولید کد، کیفیت بررسی، مدیریت، هماهنگی و مستندسازی تغییرات کاهش پیدا نکند.

Trace باید به هر تیم کمک کند بداند:

* چه چیزی تغییر کرده است
* چه کسی آن را تغییر داده است
* چرا این تغییر انجام شده است
* هدف تغییر چه بوده است
* نتیجه واقعی چه شده است
* آیا تغییر درست و کامل است
* چه ریسک‌هایی دارد
* چه بخش‌هایی تحت تأثیر قرار گرفته‌اند
* چه افرادی باید از آن مطلع شوند
* چه اقدامی باید در ادامه انجام شود
* چه اطلاعاتی باید در تاریخچه پروژه ثبت شوند

# تعریف نهایی

**Trace یک سیستم باز و قابل‌حمل برای بررسی، ثبت و مدیریت تغییرات پروژه‌های نرم‌افزاری است که می‌تواند به‌صورت ابری یا محلی اجرا شود و تمام خروجی‌های مهم خود را در ساختار استاندارد `.trace` نگه‌داری کند.**

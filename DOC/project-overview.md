# Trace چیست؟

## معرفی کوتاه

**Trace یک سیستم قابل‌حمل برای فهم، بررسی، ثبت و مدیریت تغییرات پروژه‌های نرم‌افزاری است.**

Trace تغییرات ایجادشده توسط برنامه‌نویسان و عامل‌های هوش مصنوعی را از حالت پراکنده و فنی خارج می‌کند و آن‌ها را به اطلاعات روشن، قابل‌بررسی و قابل‌اقدام تبدیل می‌کند.

Trace به تیم کمک می‌کند بداند:

- چه چیزی تغییر کرده است
- چرا تغییر انجام شده است
- هدف تغییر چه بوده است
- نتیجه واقعی چه شده است
- کدام بخش‌های پروژه تحت تأثیر قرار گرفته‌اند
- چه ریسک‌ها، تصمیم‌ها یا کارهای ناقصی ایجاد شده‌اند
- آیا چند تغییر هم‌زمان با یکدیگر ناسازگار هستند
- چه موضوعی واقعاً به توجه انسانی نیاز دارد

Trace فقط وضعیت امروز پروژه را نشان نمی‌دهد. این سیستم دانشی ماندگار از روند توسعه، تصمیم‌ها و پیامد تغییرات می‌سازد تا فهم پروژه با گذشت زمان از بین نرود.

> **Git تاریخچه کد است؛ Trace تاریخچه فهم پروژه است.**

---

## چرا Trace لازم است؟

هوش مصنوعی سرعت تولید کد را به‌شکل قابل‌توجهی افزایش داده است. یک برنامه‌نویس اکنون می‌تواند در مدت کوتاه‌تری تغییرات بیشتری ایجاد کند و چند عامل هوش مصنوعی نیز می‌توانند هم‌زمان روی بخش‌های مختلف یک پروژه کار کنند.

اما افزایش سرعت تولید کد، ظرفیت انسانی برای بررسی، فهم، هماهنگی و ثبت تصمیم‌ها را به همان اندازه افزایش نمی‌دهد.

در نتیجه، گلوگاه اصلی به‌تدریج از «نوشتن کد» به این موارد منتقل می‌شود:

- فهمیدن حجم زیادی از تغییرات
- تشخیص تغییرات مهم از تغییرات عادی
- بررسی اینکه نتیجه با هدف اولیه هماهنگ است یا نه
- شناسایی تداخل میان فعالیت افراد و عامل‌ها
- حفظ تصمیم‌ها و دلایل تغییرات
- جلوگیری از ورود تغییرات پرریسک یا ناقص
- نگه‌داشتن تصویر کلی پروژه برای تیم و مدیر

ابزارهای فعلی معمولاً بخشی از این مسئله را حل می‌کنند. بعضی ابزارها روی پیدا کردن خطا در یک Pull Request تمرکز دارند. بعضی دیگر نمودارهای مدیریتی تولید می‌کنند. برخی نیز مستندات یا خلاصه تغییرات می‌سازند.

مشکل این است که این اطلاعات اغلب پراکنده، موقت، وابسته به یک سرویس خاص یا فاقد ارتباط روشن با هدف و تصمیم‌های پروژه هستند.

Trace برای اتصال این بخش‌های جدا از یکدیگر ساخته می‌شود.

---

## مسئله‌ای که Trace حل می‌کند

در پروژه‌های نرم‌افزاری مدرن، اطلاعات مهم معمولاً میان مکان‌های مختلف پخش می‌شوند:

- Commitها نشان می‌دهند کدام خطوط تغییر کرده‌اند
- Pull Requestها بخشی از گفت‌وگو را نگه می‌دارند
- Issueها و Taskها هدف کار را توضیح می‌دهند
- پیام‌های تیم دلیل بعضی تصمیم‌ها را ثبت می‌کنند
- مدیران وضعیت پروژه را در جلسات یا گزارش‌های جداگانه دنبال می‌کنند
- عامل‌های هوش مصنوعی نیز ممکن است استدلال و تصمیم خود را فقط در یک جلسه موقت نگه دارند

پس از مدتی، پاسخ به سؤال‌های ساده دشوار می‌شود:

- چرا این بخش از سیستم به این شکل ساخته شد؟
- این تغییر دقیقاً کدام مشکل را حل کرد؟
- آیا کار واقعاً کامل شد یا فقط Pull Request بسته شد؟
- این تصمیم هنوز معتبر است یا بعداً تغییر کرد؟
- چه ریسکی پذیرفته شد؟
- کدام بخش دیگر پروژه از این تغییر تأثیر می‌گیرد؟
- آیا دو تیم در حال ساخت راه‌حل‌های متناقض هستند؟

Trace این اطلاعات را به یک روایت مستند، قابل‌ردیابی و همراه با پروژه تبدیل می‌کند.

---

# ایده اصلی Trace

Trace یک «ربات کامنت‌گذار» نیست. نقش اصلی آن ساختن یک لایه مشترک برای فهم و کنترل تغییرات است.

هر تغییر مهم باید بتواند به یک زنجیره قابل‌فهم متصل شود:

> نیاز یا هدف → تصمیم → تغییر کد → بررسی → نتیجه → اثر و اقدام بعدی

Trace تلاش می‌کند این زنجیره را از میان اطلاعات موجود پیدا کند، بخش‌های گمشده را مشخص کند و نتیجه را به‌شکل قابل‌خواندن ثبت کند.

این موضوع باعث می‌شود تغییرات پروژه فقط مجموعه‌ای از Diffها نباشند؛ بلکه به دانشی تبدیل شوند که برنامه‌نویس، تیم، مدیر و عامل‌های آینده بتوانند از آن استفاده کنند.

# پوشه `.trace`

در ریشه هر پروژه، یک پوشه مخفی با نام `.trace` می‌تواند وجود داشته باشد.

این پوشه محل استاندارد نگه‌داری خروجی‌های مهم Trace است. خروجی‌ها باید تا حد ممکن:

- قابل‌خواندن برای انسان باشند
- قابل‌استفاده برای ابزارها و عامل‌های هوش مصنوعی باشند
- همراه Repository باقی بمانند
- به یک ارائه‌دهنده یا مدل خاص وابسته نباشند
- قابل‌بررسی و قابل‌ممیزی باشند
- در صورت خروج کاربر از سرویس Trace از بین نروند

`.trace` منبع اصلی دانش قابل‌حمل پروژه است. داشبورد Trace این اطلاعات را نمایش و مدیریت می‌کند، اما قرار نیست تنها مکان نگه‌داری آن‌ها باشد.

## چه چیزهایی می‌توانند در `.trace` قرار بگیرند؟

- گزارش‌های روزانه و دوره‌ای
- گزارش هر Pull Request
- خلاصه تغییرات مهم
- تصمیم‌های ثبت‌شده
- ریسک‌های جدید، تغییرکرده یا رفع‌شده
- کارهای ناقص و موارد باقی‌مانده
- قوانین و انتظارات تیم
- هشدارهای مربوط به تداخل تغییرات
- ارتباط تغییرات با Issueها، Taskها و اهداف
- نتیجه بررسی و تأیید انسانی
- اطلاعات لازم برای نمایش و جست‌وجو در داشبورد

## چه چیزهایی نباید در `.trace` قرار بگیرند؟

- رمز عبور، API Key یا Token
- اطلاعات ورود و دسترسی
- اطلاعات شخصی یا محرمانه غیرضروری
- مکالمه‌های خام و طولانی عامل‌های هوش مصنوعی
- فایل‌های موقت و Cacheهای سنگین
- نسخه کامل کد یا Diffهای بزرگی که از قبل در Git وجود دارند
- اطلاعات داخلی سرویس Trace که برای فهم پروژه ارزشی ندارند

`.trace` باید کوچک، روشن، امن و قابل‌حمل باقی بماند.

# گزارش‌های روزانه

Trace می‌تواند تغییرات یک بازه ۲۴ ساعته را بررسی کند و در صورت وجود تغییر معنادار، یک گزارش روزانه بسازد.

گزارش روزانه فقط فهرست Commitها نیست. باید توضیح دهد در پروژه واقعاً چه اتفاقی افتاده است.

یک گزارش مناسب باید تا حد امکان به این سؤال‌ها پاسخ دهد:

- چه قابلیت‌ها یا رفتارهایی تغییر کردند؟
- هدف این تغییرات چه بود؟
- چرا انجام شدند؟
- چه افراد یا عامل‌هایی در آن نقش داشتند؟
- کدام بخش‌های پروژه تحت تأثیر قرار گرفتند؟
- نتیجه با هدف اولیه هماهنگ بود یا نه؟
- چه تصمیم‌های مهمی گرفته شد؟
- چه ریسک‌هایی اضافه، کاهش یا رفع شدند؟
- چه کاری هنوز کامل نشده است؟
- آیا تیم یا بخش دیگری باید از این تغییر مطلع شود؟
- چه اقدام انسانی یا فنی در ادامه لازم است؟

اگر تغییری وجود نداشته باشد، Trace نباید گزارش خالی و بی‌ارزش تولید کند.

هدف گزارش روزانه این نیست که فعالیت مصنوعی ایجاد کند. هدف آن کاهش زمان لازم برای ساختن تصویر ذهنی از وضعیت پروژه است.

---

# بررسی Pull Requestها

Trace می‌تواند هر Pull Request را در ارتباط با هدف، قوانین تیم و وضعیت کلی پروژه بررسی کند.

در این بررسی، Trace می‌تواند:

- هدف تغییر را به‌طور خلاصه توضیح دهد
- تفاوت میان هدف اعلام‌شده و نتیجه واقعی را مشخص کند
- بخش‌ها و قابلیت‌های تحت تأثیر را نشان دهد
- ریسک‌های مهم را برجسته کند
- ضعف یا نبود شواهد کافی برای کامل‌بودن کار را اعلام کند
- قوانین یا تصمیم‌های مرتبط پروژه را پیدا کند
- موارد نیازمند بررسی انسانی را جدا کند
- شخص یا نقش مناسب برای بررسی را پیشنهاد دهد
- نتیجه نهایی را در `.trace` ثبت کند

Trace نباید برای هر تغییر کوچک تعداد زیادی Comment تولید کند. تعداد زیاد خروجی، کیفیت پایین را جبران نمی‌کند.

اصل Trace این است:

> **یافته کمتر، اما مهم‌تر، قابل‌اثبات‌تر و قابل‌اقدام‌تر.**

# تشخیص تداخل میان تغییرات هم‌زمان

یکی از مهم‌ترین قابلیت‌های Trace، بررسی تغییرات در کنار یکدیگر است؛ نه فقط بررسی هر Pull Request به‌صورت جداگانه.

دو تغییر ممکن است به‌تنهایی درست به‌نظر برسند، اما در کنار هم مشکل ایجاد کنند.

برای مثال:

- دو Pull Request یک قابلیت مشابه را به دو روش متفاوت پیاده‌سازی می‌کنند
- یک تیم ساختار داده را تغییر می‌دهد، اما تیم دیگر همچنان روی ساختار قبلی کار می‌کند
- دو تغییر درباره نحوه احراز هویت تصمیم‌های متفاوتی می‌گیرند
- یک Migration باید قبل از تغییر دیگری منتشر شود، اما ترتیب آن مشخص نشده است
- دو عامل هوش مصنوعی براساس فرض‌های معماری ناسازگار کد تولید می‌کنند
- یک تغییر هدف یا تصمیمی را نقض می‌کند که در تغییر دیگری ثبت شده است

Trace باید این نوع ناسازگاری‌ها را زودتر از Merge یا انتشار نشان دهد.

این قابلیت از یک Merge Conflict ساده متفاوت است. Merge Conflict معمولاً برخورد مستقیم فایل‌ها یا خطوط را نشان می‌دهد. Trace باید بتواند تداخل مفهومی، محصولی و تصمیمی را نیز توضیح دهد.

# تصمیم‌ها، ریسک‌ها و کارهای ناقص

بخش مهمی از تاریخچه پروژه در کد قابل‌مشاهده نیست.

گاهی یک تیم آگاهانه یک ریسک را می‌پذیرد. گاهی یک راه‌حل موقت انتخاب می‌شود. گاهی بخشی از کار برای مرحله بعد باقی می‌ماند. گاهی یک تصمیم قدیمی با تصمیم جدید جایگزین می‌شود.

Trace باید بتواند این موارد را ثبت و در طول زمان دنبال کند.

## تصمیم

یک تصمیم می‌تواند شامل این اطلاعات باشد:

- چه مسئله‌ای وجود داشت
- چه گزینه‌هایی مطرح بودند
- چه انتخابی انجام شد
- دلیل انتخاب چه بود
- چه بخش‌هایی از پروژه تحت تأثیر هستند
- آیا تصمیم بعداً تغییر یا منسوخ شده است

## ریسک

یک ریسک می‌تواند نشان دهد:

- چه چیزی ممکن است اشتباه شود
- احتمال یا اثر آن چقدر جدی است
- چه شواهدی باعث ثبت ریسک شده‌اند
- چه کسی یا چه تیمی باید آن را دنبال کند
- آیا ریسک پذیرفته، کاهش یا رفع شده است

## کار ناقص

Trace باید بتواند فرق میان «Merge شدن» و «کامل شدن» را نشان دهد.

ممکن است یک تغییر Merge شده باشد، اما هنوز:

- تست‌های لازم کامل نشده باشند
- مستندات به‌روزرسانی نشده باشند
- Migration اجرا نشده باشد
- قابلیت پشت Feature Flag باقی مانده باشد
- بخش دیگری از محصول نیاز به هماهنگی داشته باشد
- یک راه‌حل موقت نیازمند بازنگری باشد

ثبت این وضعیت از گم‌شدن تعهدها جلوگیری می‌کند.

# قوانین اختصاصی هر تیم

Trace نباید همه پروژه‌ها را با یک الگوی ثابت بررسی کند.

هر تیم می‌تواند مشخص کند:

- چه نوع تغییراتی حساس هستند
- چه استانداردهایی اهمیت بیشتری دارند
- کدام بخش‌ها نیازمند بررسی دقیق‌تر هستند
- چه چیزی باید باعث هشدار شود
- چه یافته‌هایی باید به Pull Request اضافه شوند
- چه مواردی فقط در گزارش ثبت شوند
- چه زمانی بررسی انسانی اجباری است
- چه اطلاعاتی اجازه خروج از محیط محلی را دارند
- چه چیزی باید در `.trace` ماندگار شود

قوانین باید متعلق به خود تیم باشند. Trace باید اجرای آن‌ها را شفاف کند، نه اینکه تصمیم‌های پنهان و غیرقابل‌توضیح به تیم تحمیل کند.

# شواهد و اعتماد

اعتماد یکی از اصول اصلی Trace است.

Trace نباید یک ادعای مهم را فقط به این دلیل نمایش دهد که مدل هوش مصنوعی آن را محتمل می‌داند.

هر یافته مهم باید تا حد امکان به شواهد مرتبط متصل باشد، مانند:

- Commit یا Pull Request
- Issue یا Task
- تصمیم ثبت‌شده
- بخش مشخصی از پروژه
- نتیجه تست یا بررسی موجود
- قانون تیم
- مالک یا بخش مرتبط

Trace باید تفاوت میان این حالت‌ها را روشن نگه دارد:

- واقعیت قابل‌اثبات
- نتیجه یک قانون مشخص
- تحلیل احتمالی
- موضوعی که نیازمند تأیید انسانی است

اطمینان پایین نباید پشت زبان قطعی پنهان شود.

همچنین Trace باید نشان دهد هر گزارش:

- چه زمانی ساخته شده است
- با استفاده از چه منابعی ساخته شده است
- محلی یا ابری تولید شده است
- آیا توسط انسان بررسی یا تأیید شده است
- آیا بعداً اصلاح یا جایگزین شده است

# روش‌های استفاده از Trace

Trace باید بتواند با نیازهای مختلف حریم خصوصی و مدیریت سازگار شود.

## ۱. Trace Cloud

در این حالت، کاربر Repository خود را به سرویس Trace متصل می‌کند و فرایند تحلیل، گزارش‌سازی، زمان‌بندی و مدیریت از طریق سرویس Trace انجام می‌شود.

این مدل برای تیم‌هایی مناسب است که:

- راه‌اندازی ساده و خودکار می‌خواهند
- می‌خواهند گزارش‌ها بدون اجرای دستی تولید شوند
- چند Repository یا تیم را از یک داشبورد مدیریت می‌کنند
- به هماهنگی و گزارش‌های مرکزی نیاز دارند

## ۲. Trace Skill محلی

در این حالت، کاربر Trace Skill را داخل محیط پروژه خود اجرا می‌کند.

گزارش‌ها و خروجی‌های `.trace` در محیط خود کاربر ساخته می‌شوند. کاربر می‌تواند مدل یا ابزار موردنظر خود را انتخاب کند و لازم نیست کد پروژه را در اختیار سرویس Trace قرار دهد.

این مدل برای این گروه‌ها مناسب است:

- توسعه‌دهندگان فردی
- پروژه‌های خصوصی
- تیم‌های حساس به مالکیت فکری
- سازمان‌هایی که اجازه ارسال کد به سرویس خارجی ندارند
- تیم‌هایی که زیرساخت و مدل‌های خود را ترجیح می‌دهند

## ۳. حالت Hybrid

در مدل ترکیبی، تحلیل در محیط محلی انجام می‌شود، اما خروجی‌های انتخاب‌شده در داشبورد Trace مدیریت می‌شوند.

در این حالت:

- کد اصلی می‌تواند داخل محیط خصوصی باقی بماند
- فقط اطلاعات مجاز و انتخاب‌شده همگام می‌شوند
- مدیر دید مرکزی خود را حفظ می‌کند
- چند پروژه می‌توانند بدون ارسال کامل کد در یک داشبورد دیده شوند

کاربر باید دقیقاً بداند چه اطلاعاتی همگام می‌شوند و بتواند این محدوده را کنترل کند.

# داشبورد Trace

داشبورد Trace محل مشاهده، جست‌وجو، هماهنگی و مدیریت خروجی‌ها است؛ نه تنها منبع حقیقت پروژه.

داشبورد می‌تواند این موارد را نمایش دهد:

- تغییرات مهم اخیر
- گزارش‌های روزانه و دوره‌ای
- Pull Requestهای نیازمند توجه
- تداخل‌های شناسایی‌شده
- تصمیم‌ها و تغییر وضعیت آن‌ها
- ریسک‌ها و روند آن‌ها
- کارهای ناقص و وابستگی‌ها
- وضعیت اهداف و نیازهای پروژه
- بخش‌ها و تیم‌های تحت تأثیر
- منشأ هر گزارش: محلی، ابری یا ترکیبی
- وضعیت تأیید و بازبینی گزارش‌ها

داشبورد باید به مدیر کمک کند سریع‌تر بفهمد چه چیزی مهم است، نه اینکه حجم بیشتری از داده خام ایجاد کند.

---

# خروجی برای برنامه‌نویس

Trace باید برای برنامه‌نویس یک ابزار مفید باشد، نه یک سیستم نظارتی.

برنامه‌نویس باید بتواند بفهمد:

- تغییر او چه هدفی را دنبال کرده است
- نتیجه تا چه حد با هدف هماهنگ است
- چه بخش‌های دیگری تحت تأثیر قرار می‌گیرند
- چه ریسک یا کار ناقصی وجود دارد
- کدام قانون تیم رعایت نشده است
- چه یافته‌ای واقعاً نیازمند اصلاح است
- چه شواهدی پشت هر یافته وجود دارد
- اقدام بعدی چیست

خروجی باید کوتاه، مشخص و قابل‌اقدام باشد.

---

# خروجی برای تیم

Trace باید به اعضای تیم کمک کند تصویر مشترکی از تغییرات داشته باشند.

تیم باید بتواند ببیند:

- در هر بخش پروژه چه اتفاقی افتاده است
- چه قابلیت‌هایی در حال تغییر هستند
- چه تصمیم‌هایی گرفته شده‌اند
- کدام تغییرات روی یکدیگر اثر می‌گذارند
- چه وابستگی یا ترتیب اجرایی وجود دارد
- چه مواردی هنوز ناقص هستند
- چه هماهنگی‌هایی باید قبل از ادامه انجام شوند

هدف، جلوگیری از دوباره‌کاری، تناقض و غافلگیری در مراحل پایانی است.

---

# خروجی برای مدیر و رهبر فنی

مدیر یا رهبر فنی باید بتواند بدون خواندن تمام Commitها و Pull Requestها بفهمد:

- چه تغییرات معناداری انجام شده‌اند
- هدف و نتیجه هر تغییر مهم چه بوده است
- کدام موارد نیازمند توجه انسانی هستند
- چه ریسک‌هایی در حال افزایش یا کاهش هستند
- آیا قوانین تیم رعایت شده‌اند
- چه تصمیم‌هایی گرفته یا جایگزین شده‌اند
- چه تغییراتی میان تیم‌ها یا عامل‌ها ناسازگار هستند
- کدام کارها ظاهراً بسته شده اما هنوز کامل نیستند
- وضعیت کلی فهم و سلامت تغییرات پروژه چگونه است

این دید باید بر کیفیت پروژه و هماهنگی سیستم تمرکز کند، نه رتبه‌بندی افراد.

# Trace چه چیزی نیست؟

## Trace ابزار تولید کد نیست

ممکن است در آینده با ابزارهای تولید کد همکاری کند، اما نقش اصلی آن ساختن و کنترل‌کردن کد نیست.

## Trace جایگزین تمام ابزارهای بررسی کیفیت و امنیت نیست

ابزارهای تخصصی برای تست، امنیت و بررسی قطعی کد وجود دارند. Trace باید از خروجی آن‌ها استفاده کند و اطلاعات را به یکدیگر متصل کند، نه اینکه همه آن‌ها را دوباره بسازد.

## Trace فقط یک خلاصه‌ساز Pull Request نیست

خلاصه‌سازی یکی از خروجی‌ها است. ارزش اصلی Trace در ارتباط‌دادن هدف، تغییر، تصمیم، ریسک و تاریخچه پروژه است.

## Trace نباید یک ربات پرسر‌وصدای Code Review باشد

Commentهای زیاد، سبک‌سنجی غیرضروری و پیشنهادهای احتمالی ضعیف اعتماد تیم را از بین می‌برند.

## Trace ابزار امتیازدهی به برنامه‌نویسان نیست

تعداد Commit، تعداد خطوط کد، تعداد Pull Request یا میزان استفاده از هوش مصنوعی معیار قابل‌اعتمادی برای کیفیت فرد نیستند.

Trace نباید:

- افراد را رتبه‌بندی کند
- امتیاز بهره‌وری فردی بسازد
- فعالیت کیبورد یا زمان حضور را دنبال کند
- مدیر را به قضاوت ساده‌سازی‌شده درباره افراد تشویق کند

گزارش مربوط به افراد فقط باید برای فهم مالکیت، هماهنگی و زمینه فعالیت استفاده شود.

# اصول محصول

## ۱. وضوح به‌جای حجم

Trace باید اطلاعات مهم را جدا کند، نه اینکه داده بیشتری روی کاربر بریزد.

## ۲. شواهد به‌جای ادعای مبهم

هر یافته مهم باید قابل‌ردیابی و قابل‌بررسی باشد.

## ۳. حافظه قابل‌حمل به‌جای قفل‌شدن در یک سرویس

دانش پروژه باید همراه پروژه باقی بماند.

## ۴. کنترل کاربر به‌جای تصمیم پنهان

تیم باید قوانین، سطح حساسیت و نحوه همگام‌سازی را کنترل کند.

## ۵. حریم خصوصی از ابتدا

کاربر باید بتواند Trace را بدون ارسال کد به Cloud استفاده کند.

## ۶. همکاری انسان و هوش مصنوعی

Trace باید موارد مهم را برای انسان آماده کند، نه اینکه مسئولیت تصمیم‌های حساس را پنهانی جایگزین کند.

## ۷. هماهنگی سیستم به‌جای نظارت بر افراد

تمرکز باید روی تغییرات، ریسک‌ها، تصمیم‌ها و وابستگی‌های پروژه باشد.

## ۸. حفظ تاریخچه بدون ایجاد بدهی مستندات

گزارش‌ها باید مشخص کنند چه زمانی قدیمی یا جایگزین شده‌اند. متن قدیمی نباید بدون هشدار به‌عنوان واقعیت فعلی استفاده شود.

# کاربران اصلی Trace

Trace برای این گروه‌ها بیشترین ارزش را دارد:

- تیم‌های نرم‌افزاری که از چند ابزار یا عامل هوش مصنوعی استفاده می‌کنند
- تیم‌هایی که حجم Pull Request و تغییرات آن‌ها رو به افزایش است
- رهبران فنی که باید تغییرات هم‌زمان را هماهنگ کنند
- مدیران مهندسی که به گزارش روشن و غیرنظارتی نیاز دارند
- تیم‌های Remote و توزیع‌شده
- آژانس‌هایی که چند پروژه را هم‌زمان مدیریت می‌کنند
- سازمان‌های حساس به حریم خصوصی و مالکیت کد
- پروژه‌هایی که تاریخچه تصمیم و دلیل تغییرات برای آن‌ها اهمیت دارد
- تیم‌هایی که چند Repository یا سرویس وابسته دارند

مشتری اولیه مناسب برای Trace، تیمی است که درد واقعی هماهنگی و از دست‌رفتن زمینه را تجربه می‌کند؛ نه تیمی که فقط یک خلاصه خودکار دیگر می‌خواهد.

# تفاوت Trace با دسته‌های موجود

## در مقایسه با ابزارهای AI Code Review

Trace نباید با وعده «پیدا کردن تعداد بیشتری Bug» وارد رقابت مستقیم شود. تفاوت آن باید در فهم روند تغییرات، تداخل میان کارهای هم‌زمان، شواهد، حافظه پروژه و قابل‌حمل‌بودن خروجی‌ها باشد.

## در مقایسه با داشبوردهای مهندسی

Trace نباید صرفاً نمودارهای سرعت و فعالیت تولید کند. تمرکز آن باید روی معنای تغییرات، تصمیم‌ها، ریسک‌ها و اقدام بعدی باشد.

## در مقایسه با ابزارهای مستندسازی

Trace نباید فقط صفحات متنی تولید کند. هر گزارش باید به تغییر واقعی، زمان، هدف و شواهد خود متصل باشد و در صورت قدیمی‌شدن قابل‌تشخیص باشد.

## در مقایسه با حافظه داخلی عامل‌های هوش مصنوعی

حافظه Trace باید برای تیم قابل‌مشاهده، قابل‌ویرایش، قابل‌انتقال و مستقل از یک مدل یا ابزار خاص باشد.

# موفقیت Trace چگونه سنجیده می‌شود؟

موفقیت Trace با تعداد Comment یا حجم گزارش‌ها سنجیده نمی‌شود.

نشانه‌های واقعی ارزش محصول عبارت‌اند از:

- تیم‌ها گزارش‌ها را واقعاً می‌خوانند
- یافته‌ها باعث اقدام مشخص می‌شوند
- تداخل‌ها زودتر شناسایی می‌شوند
- مدیر زمان کمتری برای فهم وضعیت پروژه صرف می‌کند
- تصمیم‌های مهم کمتر گم می‌شوند
- افراد و عامل‌های جدید سریع‌تر زمینه پروژه را درک می‌کنند
- نرخ یافته‌های ردشده و کم‌ارزش پایین می‌ماند
- تیم قوانین خود را به‌مرور دقیق‌تر می‌کند
- اطلاعات پس از قطع سرویس همچنان قابل‌استفاده باقی می‌مانند

اگر گزارش‌ها خوانده نشوند، بیش از حد عمومی باشند یا اعتماد تیم را کاهش دهند، Trace ارزش خود را ثابت نکرده است.

# مسیر کلی محصول

Trace باید ابتدا روی یک مسئله محدود و قابل‌اثبات تمرکز کند:

> فهم تغییرات مهم، تشخیص تداخل میان کارهای فعال و ثبت نتیجه در یک ساختار قابل‌حمل.

پس از اثبات این ارزش، محصول می‌تواند به‌تدریج حوزه‌های بیشتری مانند هماهنگی میان چند پروژه، سیاست‌های سازمانی، گزارش‌های دوره‌ای و اتصال به ابزارهای بیشتر را پوشش دهد.

Trace نباید از ابتدا تلاش کند تمام فرایند مهندسی نرم‌افزار را جایگزین کند.

# هدف نهایی

هدف Trace این است که افزایش سرعت تولید کد باعث کاهش کیفیت فهم، بررسی، هماهنگی و تصمیم‌گیری نشود.

Trace باید کاری کند که هر تغییر مهم قابل‌پاسخ‌گویی باشد:

- چه چیزی تغییر کرد؟
- چرا تغییر کرد؟
- هدف چه بود؟
- نتیجه چه شد؟
- چه چیزهایی تحت تأثیر قرار گرفتند؟
- چه تصمیم یا ریسکی ایجاد شد؟
- آیا با تغییر دیگری ناسازگار است؟
- چه اقدامی هنوز باقی مانده است؟
- چه کسی باید موضوع را بررسی یا دنبال کند؟
- شواهد این نتیجه کجا هستند؟

# تعریف نهایی

**Trace لایه قابل‌حمل حافظه، هماهنگی و حاکمیت تغییرات برای تیم‌های نرم‌افزاری انسانی و مبتنی بر هوش مصنوعی است. این سیستم تغییرات پراکنده را به دانشی روشن، مستند و قابل‌اقدام تبدیل می‌کند و نتیجه را در ساختار استاندارد `.trace` همراه پروژه نگه می‌دارد.**
